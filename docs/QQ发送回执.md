# QQ 发送动作与真实回执

`QqSendActions` 在独立适配器一侧保存每个发送动作，而不是等整份脚本、整轮模型或主线程收尾
后才记录。`qq.replyScope` 缺省为 `private`，显式 `all` 允许群聊和私信；动作层和传输层均检查实际授权范围。
更改权限不重放旧动作，包括曾因 scope 失败的动作。健康状态报告实际范围。

## 动作编号与恢复

调用方给一个实际动作固定的 actionId、目的地、正文、被动回复编号和序号。参数先按传输契约
预检，再将完整请求摘要与 started 记录持久化，之后才开始网络发送。
同编号并发等待同一次真实执行，相同请求采用已有回执；不同请求复用同编号则拒绝冲突。

平台给出真实消息编号才保存 sent；明确失败保留 failed 与 attempted；没有编号、超时、异步审核等保留
unknown。所有结果先写终态、同步文件与目录，再返回调用方。JSON 序列化前后
回执结构一致，缺失的可选字段不会在重启后变成另一份形状。

发送中宿主被终止，重启看到 started 但无终态，返回 interrupted/unknown，不自动重发。
实际发送成功却回执写入失败也不能宣称已持久完成，当前实例关闭后明确报存盘错误；恢复时仍保留
started/unknown，等待已有副作用核对。当前组件没有平台查询原动作或审核回调，不擅自把 unknown 改成
failed/sent，也不通过改序号重发猜测是否成功。

正式脚本/意识流已按持久模型响应与脚本执行生成
actionId，并在恢复时采用原动作。如果模型用新编号重复提出同一发送，
本组件不能单靠正文相同认定它是旧动作，也不能证明根源重复触发已经全消失。
入站平台去重负责防止同一事件再触发，脚本恢复还必须引用原动作编号。

## 生命周期与数据

发送目录有排他锁，同目录第二实例不能写。关闭先停止接新动作，再等实际在途执行与保存，
然后释放锁；不能让旧动作迟到完成时与新实例同时写。这个组件的锁不替代守护的所有权令牌，
不能允许两个不同目录的实例同时持有线上手机。

原请求与回执存于 0600 文件，正文和平台标识属于业务事实，不在诊断日志打印，也不作为缓存
随便删除。损坏、未知文件或未完成临时文件保留并报错。启动读取全量动作索引，尚未做分段或
大规模索引；当前仅适合重做测试规模。恢复校验参数摘要、记录结构和结果状态，不把字符串
“发送成功”当作平台回执。

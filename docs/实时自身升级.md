# 实时自身升级

实时升级由固定宿主桥与候选监督器协作完成：Eve 修改并提交源码，用 `prepare_self_upgrade` 冻结候选，再调用 `apply_self_upgrade` 提交摘要。当前回复送达且会话空闲后，监督器关闭旧业务进程并交接；固定桥验证并启动候选的业务程序和 Python 运行脚本，不需要用户手动重启。切换期间 QQ 会短暂重连。

## 装配

开发工具配置继续使用现有的可信操作者名单和独立账本，增加 `live_upgrade`。例如：

```json
{
  "workspace": "/srv/eve/source",
  "storage_directory": "/srv/eve/developer",
  "operators": ["填写 /help identity 的实际标识"],
  "commands": true,
  "self_upgrade": true,
  "live_upgrade": "/srv/eve/upgrade"
}
```

设置 `EVE_DEVELOPER_CONFIG` 后，Linux 宿主固定部署 `host_runtime_bridge.py`、`host_runtime_contract.py` 与初始三个运行脚本，再启动原来的 QQ 命令。首次没有活动候选时，`--source-revision` 必须来自宿主实际验收的干净部署提交：

```sh
python3 -I -B /srv/eve/runtime/host_runtime_bridge.py \
  --supervisor /srv/eve/runtime/self_upgrade_runtime.py \
  --directory /srv/eve/upgrade \
  --candidates /srv/eve/developer/candidates \
  --source-revision 填写实际验收的40位提交摘要 -- \
  /srv/eve/bin/eve-qqbot --state-dir /srv/eve/state \
  --agent /srv/eve/source/AGENT.md \
  --bridge-script /srv/eve/source/connectors/qqbot/bridge.mjs \
  --memory --self-learning
```

模型只提交 `candidate_sha256`，不能通过工具参数指定程序、目录、身份或停机命令。监督器的候选根目录与开发账本对应。准备新候选也必须有在线监督器提供准确源码基线；未知基线拒绝准备。已有活动候选的基线只取已验证清单，不能用启动参数覆盖旧版未提交的改动。

当前交接门支持文件状态后端；遇到 `--database-config` 明确拒绝启动。完整运行脚本交接目前要求 Linux 固定宿主桥。旧单层监督器仍可读取旧候选、执行旧版恢复和重启；新运行包候选在缺少固定桥时明确拒绝，不降级成仅更新二进制。Windows 的旧流程继续使用独立进程组 Ctrl+Break 收尾。

## 应用与确认

自然聊天请求重启时，模型可直接调用无参数 `restart_self`。宿主只接受主人或管理员的可信当前会话与持久轮次，后台、子代理和脚本插件不能代办；动作仍经独立审核。监督器必须声明支持重启，旧监督器缺少该字段时拒绝排队。`queued: true, restarted: false` 仅表示等待回复送达和空闲，账本记为待确认；后续查询 `self_upgrade_status` 的 `restarted` 才证明实际完成。

Rust 开发后端读取监督器、候选清单、租约及已有请求时，按 1 MiB 上限分块读取；冻结资源每文件至多 8 MiB、合计 64 MiB，构建程序至多 2 GiB，与切换校验对齐。大小检查不只依赖读取前的 metadata，文件在读取期间增长也会被上限阻断。正文缓冲申请不按超过上限的长度扩容，申请失败返回错误；不覆盖原文件或以新请求重试。大文件摘要核对和二进制/资源读取在块间及 EOF 后检查原取消与期限，不能承诺中断底层已经阻塞的单次文件系统调用。授权、内容摘要、验证合同、租约和切换门仍按原规则执行。

1. 在当前会话的私有检出开发，仓库发布仍走 PR。准备工具把本会话改动冻结到独立候选 Git 仓库，再合并最新在线修复；共享工作区和其他会话的未提交内容不纳入候选、不提交、不覆盖。候选自身要求干净且完整可审，隐藏修改、二进制和子模块差异仍拒绝。实际通过格式、严格 Clippy、工作区测试、Python 协议验收、构建和真实候选二进制的隔离重启/交接预演后，冻结证据与资源。
2. `apply_self_upgrade({"candidate_sha256":"准备结果中的摘要"})` 只登记持久请求。`queued: true, applied: false` 不能说成“已经升级”。本轮先回复“已排队”并结束，不在当前轮轮询等待应用，否则无法满足回复送达门；应用结果在后续新轮查询。
3. 监督器再次校验准备租约、候选及资源摘要，运行 `--help`，准备 Node 依赖，再等申请的**确切持久轮次** Completed、QQ 回执 Sent 和全部会话、任务、唤醒、主动联系、群消息及文件投递空闲；默认等待至多 300 秒，持续繁忙则拒绝本次切换，旧实例继续运行。门禁同时跟踪文件投递账本、群消息 SQLite 数据库及其 WAL 的变化，最终切换前再次读取，不因主状态文件未改变而跳过。
4. 旧业务与监督器正常收尾后，固定桥重新校验清单、完整差异、租约、全部脚本与程序，启动候选监督器和业务程序。只有实际得到 `EVE_QQBOT_READY`、通过稳定窗口且随机凭证、进程和候选身份吻合，才提交活动指针。候选在提交确认前不调度下一次升级或重启。该门证明 QQ 网关已经就绪，不能当作每个模型和业务路径均已验收。
5. `self_upgrade_status` 返回心跳、当前二进制摘要、候选摘要、阶段、结果及错误码。`result: applied` 才表示成功；同一当前候选的重复申请不再次切换。

运行资源包括受 Git 管理的 AGENT、QQ 桥接、vendor 文件，以及精确三个脚本 `scripts/self_upgrade_runtime.py`、`scripts/source_update.py`、`scripts/build_resources.py`。清单的 `runtime.host_protocol` 为 1，`runtime.scripts` 固定为上述三项的排序列表，不能混入任意运行模块。固定桥只从核对过的源码字节加载这三项，不读取候选 pyc 或搜索候选目录。Node 锁文件未变时复用依赖；变更时在 `runtime-resources/<摘要>/qqbot` 缓存执行 `npm ci --ignore-scripts`，不改写候选目录，失败发生在关闭旧实例之前。缓存桥接也核对摘要，安装中断的缓存会重建。研究和继承资料指向候选快照，固定版本的外部 Mindustry/Arc 源码沿用宿主配置。

`source-diff.patch` 保存相对在线干净提交的完整 Git 差异；`source_diff` 绑定文件名、SHA-256、基线与目标提交，并纳入候选身份。原文至多 128 KiB，完整独立审核请求至多 256 KiB；超限拒绝准备，必须拆分候选，不能用摘要或截断内容代替代码。审核和应用都再次核对在线基线、差异、租约及资源。首次由宿主工程部署建立基线属于宿主验收，不能宣称模型审核过不在差异里的历史整批代码。

准备结果的候选目录以源码、完整差异、程序与资源内容摘要寻址。相同内容重复准备会校验并复用已有目录，损坏目录保留并拒绝覆盖。开发账本的 `leases/<摘要>.json` 单独保存有效期为 24 小时的准备租约；重新准备只续租。租约绑定候选摘要、原始清单、切换完整运行包并保留状态的计划、固定验证政策、四组检查证据及文件状态顶层 schema 1。`apply_self_upgrade` 仍只接收候选摘要，由可信宿主读取租约，模型不能补写字段。独立审核的允许结果不能豁免硬校验。

租约缺失、内容或计划改变、到期分别返回 `prepare_lease_missing`、`prepare_lease_changed`、`prepare_lease_expired`。排队等待期间过期也拒绝切换；活动指针里的历史租约只作来源记录，已上线程序不会因为准备租约到期而停止。此 schema 绑定不代表任意未来插件格式都可降级：候选写下旧版不能读取的状态时，回退会停止并保留状态，需要人工检查兼容性。

宿主显式指定的外部桥接适配器沿用原路径；只有随包的 `qqbot/bridge.mjs` 切到候选快照，避免替换自定义渠道适配器。外部 Node 启动器与参考源码仍由宿主管理。

## 状态、失败与恢复

任务账本格式 4 使用目录和不可变冷正文。监督器逐条核对 `task-archive` 正文的长度、摘要、任务身份及投影目录，之后判断执行和通知是否空闲；任务仍运行、通知正在投递、目录与正文不符、归档缺失或格式未知时均不切换，不修改原始数据。投影与 Rust 持久层一致：目录不复制 `execution.review_messages`，完整授权原话仍保存在经过长度与摘要核验的冷正文中，缺少这份目录副本不能误判为归档损坏。

候选在就绪阶段失败也会持久隔离；相同候选再次提交会被拒绝，修复后须生成新候选。活动指针提交前先完成描述符校验；提交后的状态发布失败时先恢复旧磁盘指针和内存描述符，再启动旧版。恢复指针失败则停止并保留现场，不宣称回退成功。

监督器 JSON 读取和程序摘要扫描在打开文件后继续按上限读取；读取中增长、非普通文件或长度改变时拒绝验证。候选可更新三个运行脚本；固定 `host_runtime_bridge.py` 与 `host_runtime_contract.py` 不属于候选白名单，修改固定边界需要宿主单独工程部署。同一用户身份的操作系统权限并未因此被隔离，宿主仍须保护固定部署目录和配置。

`host-active.json` 绑定实际业务命令、程序摘要、源码提交及脚本摘要；`host-handoff.json` 保存准备、旧实例关闭、试运行、提交或回退阶段。指针和日志不同步时按持久事务恢复，未知组合停止保留现场；不盲目重发请求。新进程启动前先持久记录进程身份，再通过私有管道放行，外层崩溃不会留下未记载且持业务锁的子进程。外层使用自己的会话身份关闭相关进程，恢复预算保存在 `host-recovery.json`，78 或持久 blocked 不因服务重启重新放行。

`host-anchors/` 按活动记录摘要保存不可变回退关系；A 升到 B 后，尝试 C 失败回 B，仍能在 B 后续故障时退回 A，宿主重启也保留这条关系。最多 16 份、每份 128 KiB；不自动删除锚点或候选。容量不足拒绝本次交接并重新启动已验证旧版；协议初始化后缺失、损坏、冲突或循环锚点停止保留现场，不能默默丢掉回退依据。

- 定义在 `eve-developer-api`，工具实现仍在 `eve-developer-tools`；监督器独立于模型和 QQ 进程，按同一版本的文件协议交接。
- `request.json` 是待处理请求，`processing.json` 表示已进入切换；`history/` 保留原请求。未知协议、重复 JSON 字段、损坏候选、过期心跳、未经完整验证的候选或身份不匹配都会拒绝，不清空原文件。
- 申请轮次被取消/中断/失败时不切换。旧单层监督器重启归档遗留请求；固定桥接管的完整交接按持久事务核对并归档，不重新执行历史业务。旧工具调用与 QQ 消息不回放、不补发。
- 候选启动失败或提交后返回受控运行故障码 76 时，固定桥恢复上一组脚本和二进制，**保留候选已经写下的实际状态**。旧版无法读取实际状态或重新上线时停止保留现场，不能宣称回退成功。旧单层流程保留的 `backups/` 快照也不自动覆盖业务状态。
- 准备候选最多保留八份，达到上限后明确拒绝发布第九份，不自动删除可能仍被其他进程使用的旧版本；检查活动、上一版本和待处理请求后，再清理确定未使用的候选与对应运行缓存。便携更新也采用内容寻址复用和八份版本上限。源码构建日志有 32 MiB 单文件上限，只读最后 16 KiB 到内存，并保留最近两轮历史源码验收日志。
- `last-failure.json` 只记录最近失败的时间、阶段、错误码和二进制/候选摘要，不复制密钥、完整状态或会话内容。首次启动及恢复后的就绪失败都消耗同一个有限重启预算；耗尽后保留现场停止。
- 活动版本指针只在候选实际就绪后原子保存。候选上线后发生的业务故障仍由实际故障回执和现有恢复语义处理，不会无限循环重启。
- 24 小时等运行窗口应放在监督器外层计时；子进程升级不会重置原截止时间。收到停止信号后监督器先请求当前子进程正常收尾，超时保留原状态且不把强杀当作成功收尾。

可用 `python3 scripts/verify-self-upgrade.py` 并行运行四套独立真实进程验收，覆盖送达门、任务 v4 冷归档、完整脚本交接、持久事务强杀恢复、有限熔断、失败回退且不覆盖状态、资源损坏、取消和零回放；开发工具验收另核对会话与轮次来自可信宿主。

`connectors/qqbot/test/live_upgrade_test.py` 将真实 QQ 宿主、工具请求、监督器和第二个 QQ 宿主接成一次完整交接：使用本地模型和 QQ 传输替身，核对先 Sent 再切换、同条消息不重复触发模型/工具，以及两个进程都正常收尾。

源码部署可额外启用[运行版源码自动同步](./运行版源码自动同步.md)，由宿主定时拉取固定 GitHub 分支、验证候选并在运行空闲时切换；不需要伪造 QQ 申请轮次。

可在正式服务保持运行时执行 `python3 scripts/verify-self-upgrade.py --binary /绝对路径/eve-qqbot`。测试只创建自己的临时目录、本地 HTTP 服务及通道替身，启动实际 Eve 和监督器，验证重启、运行包交接与持久回执不重放。输出 `EVE_UPGRADE_EVIDENCE` 包含二进制 SHA256、各套件退出码和 `production_switched:false`。正式通道连通性和生产状态下的稳定窗口仍由最后的真实切换确认；隔离预演不会伪造这部分证据。

# 插件开发与第一阶段验收

## 依赖方向

| 目录 | 职责 |
| --- | --- |
| `crates/plugin-api` | 插件、Context、数据类型、错误及能力 Trait |
| `crates/kernel/src/backends` | 同步广播、内存服务、内存状态和声明权限检查 |
| `crates/kernel/src/context.rs` | Scope 准入、资源归属、后端调用与服务提供者状态检查 |
| `crates/example-plugins` | 只依赖 `plugin-api` 的提供者、消费者、故意失败插件 |
| `crates/runtime` | 选择后端，注册插件，执行验收 |

业务插件不能依赖 Kernel 的私有结构。服务的契约可放入独立契约 crate，消费者获取 `Arc<dyn 服务契约>`，不依赖提供者具体类型。示例中的 `FormatterService` 演示了这种方式。

## 替换后端

定义层提供 `EventBus`、`ServiceRegistry`、`StateStore` 和 `PermissionChecker`。宿主使用 `KernelServices` 单独替换任意能力：

```rust
use eve_kernel::{Kernel, KernelServices, backends::MemoryStateStore};
use std::sync::Arc;

let state = Arc::new(MemoryStateStore::default());
let kernel = Kernel::with_services(KernelServices {
    state: state.clone(),
    ..KernelServices::default()
});
```

实现自定义 `StateStore` 后，只需替换上面的实例，插件代码无需改变。每个 Kernel 默认使用独立后端；事件和服务后端应属于一个 Runtime，不能混用不同 Runtime 的插件 ID。状态后端可由同一宿主保留，用于内存内重新装配；这不等于持久化恢复。

事件订阅和服务注册返回异步 `Cleanup`，由 Kernel 加入插件 Scope。注册失败不得留下资源；清理必须只撤销对应注册。清理闭包应使用弱引用或独立令牌，避免与捕获 Context 的回调形成引用环。同步后端不得在注册方法中执行插件回调；广播时释放内部锁，允许回调使用 Context。

## Context 接口

| 方法 | 行为 |
| --- | --- |
| `emit` / `on` | 发布事件、订阅事件；监听器随 Scope 清理 |
| `provide_service` | 按字符串 ID 注册服务，重复 ID 返回错误 |
| `service::<T>` | 类型匹配返回 `Ok(Some(Arc<T>))`，缺失返回 `Ok(None)`，不匹配返回错误 |
| `state_get` / `state_set` | 在当前插件 ID 的命名空间内读写字节值 |
| `check_permission` | 请求可替换的权限检查器进行检查 |
| `cleanup` | 注册异步清理，停止时按注册逆序执行 |

此次接口调整：`service` 与 `state_get` 从 `Option` 改为 `PluginResult<Option<_>>`，调用者需要增加 `?`，以保留后端错误和 Context 关闭错误。

停止会关闭 Scope，旧 Context 的读写与注册均返回错误；插件再次启动会取得新的 Scope。已经取得的服务 `Arc` 不会被强制销毁。已经准入的同步事件回调可能与停止重叠，但旧 Context 无法在 Scope 关闭后创建新资源或写入状态。监听器的 `Err` 会被隔离并返回首个错误；本阶段不承诺隔离 Rust panic。

`DeclaredPermissionChecker` 精确匹配 Manifest 权限声明，自定义检查器可进一步拒绝权限。本阶段权限检查是可信插件遵循的 API 约定，不拦截原生插件直接调用文件、网络或进程 API。

## 验收顺序

执行 `cargo run -p eve-runtime`：

1. 只请求启动消费者，Kernel 自动先启动其提供者。
2. 提供者注册格式化服务，并订阅“消费者就绪”事件。
3. 消费者获取服务、订阅消息，再发布就绪事件。
4. 提供者响应就绪事件发布消息，消费者通过服务契约处理消息并写入自己的状态。
5. 宿主检查状态为“已接收：你好，Eve.aic”，停止消费者和提供者，验证服务已移除、停止后事件不再写状态。
6. 请求启动故意失败插件，自动重新启动提供者；故意失败插件注册服务和监听器后报错，Kernel 清理资源并回滚本次新启动的依赖。

`cargo test --workspace` 进一步检查逆序停止、失败后资源实际释放、重复服务 ID、类型错误、状态隔离、事件重入、权限拒绝、可替换后端和回滚错误保留。

状态写入不属于启动事务：停止或失败不会撤销已写入的状态。任务取消、独立 Logger、持久化状态与 Runtime 重启恢复仍属于后续阶段。

# 插件开发与第一阶段验收

## 依赖方向

| 目录 | 职责 |
| --- | --- |
| `crates/plugin-api` | 插件、Context、数据类型、错误及能力 Trait |
| `crates/kernel/src/backends` | 同步广播、内存服务、内存状态、声明权限检查、Tokio 任务和日志后端 |
| `crates/kernel/src/context.rs` | Scope 准入、资源归属、后端调用与服务提供者状态检查 |
| `crates/example-plugins` | 只依赖 `plugin-api` 的提供者、消费者、任务演示和故意失败插件 |
| `crates/runtime` | 选择后端，注册插件，执行验收 |

业务插件不能依赖 Kernel 的私有结构。服务的契约可放入独立契约 crate，消费者获取 `Arc<dyn 服务契约>`，不依赖提供者具体类型。示例中的 `FormatterService` 演示了这种方式。

## 替换后端

定义层提供 `EventBus`、`ServiceRegistry`、`StateStore`、`PermissionChecker`、`TaskManager` 和 `Logger`。宿主使用 `KernelServices` 单独替换任意能力：

```rust
use eve_kernel::{Kernel, KernelServices, backends::MemoryStateStore};
use std::sync::Arc;

let state = Arc::new(MemoryStateStore::default());
let kernel = Kernel::with_services(KernelServices {
    state: state.clone(),
    ..KernelServices::default()
});
```

实现自定义 `StateStore` 后，只需替换上面的实例，插件代码无需改变。每个 Kernel 默认使用独立后端；事件、服务和任务后端应属于一个 Runtime，不能混用不同 Runtime 的插件 ID。状态后端可由同一宿主保留，用于内存内重新装配；这不等于持久化恢复。

事件订阅和服务注册返回异步 `Cleanup`，由 Kernel 加入插件 Scope。注册失败不得留下资源；清理必须只撤销对应注册。清理闭包应使用弱引用或独立令牌，避免与捕获 Context 的回调形成引用环。同步后端不得在注册方法中执行插件回调；广播时释放内部锁，允许回调使用 Context。

## Context 接口

| 方法 | 行为 |
| --- | --- |
| `emit` / `on` | 发布事件、订阅事件；监听器随 Scope 清理 |
| `provide_service` | 按字符串 ID 注册服务，重复 ID 返回错误 |
| `service::<T>` | 类型匹配返回 `Ok(Some(Arc<T>))`，缺失返回 `Ok(None)`，不匹配返回错误 |
| `state_get` / `state_set` | 在当前插件 ID 的命名空间内读写字节值 |
| `check_permission` | 请求可替换的权限检查器进行检查 |
| `spawn_task` | 创建后台立即、延迟、指定时间或重复任务，返回 `TaskId` |
| `run_foreground` | 等待前台一次性或有限重复任务完成 |
| `tasks` | 查询当前插件任务的状态、成功次数和是否确认退出 |
| `log` | 提交级别、目标、消息和字段，由宿主附加插件身份与时间 |
| `cleanup` | 注册异步清理，停止时按注册逆序执行 |

此次接口调整：`service` 与 `state_get` 从 `Option` 改为 `PluginResult<Option<_>>`，调用者需要增加 `?`，以保留后端错误和 Context 关闭错误。

停止会关闭 Scope，旧 Context 的读写与注册均返回错误；插件再次启动会取得新的 Scope。已经取得的服务 `Arc` 不会被强制销毁。已经准入的同步事件回调可能与停止重叠，但旧 Context 无法在 Scope 关闭后创建新资源或写入状态。监听器的 `Err` 会被隔离并返回首个错误；事件监听器不隔离 Rust panic；任务 panic 由执行器捕获并记录为失败（编译为 panic=abort 时无法恢复）。

`DeclaredPermissionChecker` 精确匹配 Manifest 权限声明，自定义检查器可进一步拒绝权限。本阶段权限检查是可信插件遵循的 API 约定，不拦截原生插件直接调用文件、网络或进程 API。

## 验收顺序

执行 `cargo run -p eve-runtime`：

1. 只请求启动消费者，Kernel 自动先启动其提供者。
2. 提供者注册格式化服务，并订阅“消费者就绪”事件。
3. 消费者获取服务、订阅消息，再发布就绪事件。
4. 提供者响应就绪事件发布消息，消费者通过服务契约处理消息并写入自己的状态。
5. 任务演示执行立即、延迟、指定时间和三次重复的前台任务，共计六次，并启动后台周期任务。
6. 宿主检查状态为“已接收：你好，Eve.aic”，停止消费者和提供者，验证服务已移除、停止后事件不再写状态。
7. 请求启动故意失败插件，自动重新启动提供者；故意失败插件注册服务和监听器后报错，Kernel 清理资源并回滚本次新启动的依赖。
8. 消息处理、任务完成与预期回滚均输出结构化日志；宿主停止插件后调用 `flush_logs`。测试替换为内存后端，核验记录的来源与业务字段。

`cargo test --workspace` 进一步检查逆序停止、失败后资源实际释放、重复服务 ID、类型错误、状态隔离、事件重入、权限拒绝、可替换后端和回滚错误保留。

状态写入和日志不属于启动事务：停止或失败不会撤销已写入的状态或已接收的日志。持久化状态与 Runtime 重启恢复仍属于后续阶段。日志接口、过滤、错误处理及替换示例见[日志接入](./日志接入.md)。

## 任务模型

模式和调度独立组合。前台表示调用方等待结果，不代表 UI 线程或高优先级。前台与后台共享执行器及停止流程：

| 调度 | 语义 |
| --- | --- |
| `Immediate` | 开始执行一次 |
| `After(Duration)` | 自登记起等待指定时长再执行一次 |
| `At(SystemTime)` | 登记时转换为单调时钟上的等待时间；过期立即执行一次，之后不跟随系统时钟调整 |
| `Every { interval, runs }` | 首次立即执行，之后每次完成再等待 interval；串行执行、不重叠、不补发 |
| `Custom { name, max_runs, factory }` | 插件工厂为每个任务创建独立调度器，可等待事件、返回变化的间隔或主动结束；后端限制最大执行次数 |

`runs: Some(n)` 表示有限次数，`None` 表示后台无限重复。零间隔、零次数和前台无限重复均拒绝。公开字段被修改后，后端仍会重新校验。

```rust
use eve_plugin_api::{PluginContext, PluginResult, TaskMode, TaskSchedule, TaskSpec};
use std::{sync::Arc, time::Duration};

async fn execute(ctx: &PluginContext) -> PluginResult<()> {
    let report = ctx.run_foreground(TaskSpec::new(
        "执行三次", TaskMode::Foreground,
        TaskSchedule::Every { interval: Duration::from_secs(1), runs: Some(3) },
        Arc::new(|signal| Box::pin(async move {
            if signal.is_cancelled() { return Ok(()); }
            // 在这里执行一次业务动作。
            Ok(())
        })),
    )?).await?;
    // 登记失败为 Err；动作失败或取消在报告中，应同时检查 state 和 errors。
    println!("{:?}，已成功完成 {} 次，错误 {:?}", report.state, report.runs, report.errors);
    Ok(())
}
```

`Context::run_foreground` 在首次轮询时登记，停止后才轮询的旧 Future 会被拒绝。已经登记的前台任务在等待被丢弃时请求取消；普通返回报告包含真实成功次数、终态与错误，不将提前取消算作完整执行。启动函数内等待前台任务会推迟插件进入 Active；生命周期操作仍串行，因此这里应只等待有限、能结束的初始化工作。

## 自定义任务类型与调度

任务行为、前后台模式和调度规则彼此独立。插件可定义任意 Rust 结构体实现 `Task`，通过字段携带类型化参数、服务契约或 Context。`TaskSpec::from_task` 将 `Arc<dyn Task>` 接入统一执行路径；原有闭包入口 `TaskSpec::new` 继续可用，默认类型为 `eve.action`。

```rust
use eve_plugin_api::{
    PluginContext, PluginFuture, Task, TaskSignal, TaskTypeId,
};
use std::sync::Arc;

struct SaveValue {
    ctx: PluginContext,
    value: Vec<u8>,
    kind: TaskTypeId,
}

impl Task for SaveValue {
    fn task_type(&self) -> TaskTypeId { self.kind.clone() }

    fn execute(&self, _signal: Arc<dyn TaskSignal>) -> PluginFuture<'_, ()> {
        Box::pin(async move { self.ctx.state_set("saved", self.value.clone()) })
    }
}
```

构造 `TaskTypeId::new("my-plugin.save-value")?` 并传入上述对象，然后调用 `TaskSpec::from_task("保存", mode, schedule, Arc::new(task))?`。此类型可以组合任意内置或自定义调度，以及前台或后台模式，不需要在 Kernel 中增加枚举项或类型分支。`TaskInfo` 和 `TaskRunReport` 的 `task_type` 保存构造时的标识快照。标识用于分类与诊断，执行代码来自传入的对象；当前不提供按字符串动态发现、加载或反序列化任务的注册表。

自定义触发规则实现 `TaskScheduler::next(&mut self, completed)`，通过 `TaskSchedule::Custom` 接入：

- `factory` 在执行任务内部调用，每个任务创建独立调度状态；克隆 `TaskSpec` 也会重新创建调度器。工厂不应返回共享的可变调度游标。
- `next` 在第一次动作前和每次成功动作后调用，`completed` 是当前成功次数。可异步等待事件或条件；返回 `Some(delay)` 表示从返回时起再等待指定时长，返回 `None` 表示自然完成，允许执行零次。
- `max_runs` 是执行器强制执行的成功次数上限，达到后不再调用 `next`。前台必须设置正数上限，后台可为 `None`；次数有限不代表等待事件一定会完成，初始化过程仍须选择能结束的工作。
- 调度等待受停止信号控制，取消会丢弃等待 Future 并释放调度器，因此实现必须允许这种取消。调度及动作均不可同步阻塞执行器；动作收尾继续通过 `TaskSignal` 配合。
- 工厂或 `next` panic、`next` 返回错误以及非法延迟都归入该任务的失败报告；不会绕过现有 Scope 与停止路径。同一任务内不会并发调用调度器或动作。

查询使用 `TaskScheduleInfo`，只保存描述，不持有自定义对象、工厂闭包或调度状态，避免已完成任务记录延长插件资源寿命。迁移时将针对 `TaskInfo::schedule` 的匹配改用 `TaskScheduleInfo`；提交任务仍使用 `TaskSchedule`。

实际示例见 `crates/example-plugins/src/tasks.rs`：`WriteStateTask` 同时用于前台自定义递增间隔和后台内置周期调度。示例插件只依赖 `plugin-api`，通过 `cargo run -p eve-runtime` 可验证自定义任务执行三次并真实写入状态。事件驱动调度、取消和工厂隔离由 `crates/kernel/tests/custom_tasks.rs` 验证。未来 Cron 等策略可以经此接口扩展，当前没有内置 Cron 实现。

## 停止顺序与报告

1. 封闭新任务、服务、订阅和 Cleanup 的注册入口。已有任务此时仍可通过 Context 读写状态完成收尾。
2. 向当前插件的所有前台和后台任务发送 `TaskSignal`，共享 `KernelConfig::task_shutdown_timeout` 的期限，默认五秒。
3. 到期后对尚未退出的任务全部发出 Tokio abort，再共享 `task_abort_timeout` 的期限确认退出，默认 100 毫秒。
4. 关闭 Context 的读写能力，逆序等待已注册的异步 Cleanup。

停止报告分别列出 `stopped`（已确认退出）、`timed_out`（超过协作期限）、`unfinished`（仍未确认退出）及错误。任务收到取消后退出为 `Cancelled`，自然成功为 `Finished`，返回错误或 panic 为 `Failed`。`TimedOut` 不代表已退出；`TaskInfo::exited` 明确表达确认状态。存在未退出任务时插件进入 `Failed`，避免重复启动产生两代任务；宿主可通过 `Kernel::tasks` 查询，并持有后端再次调用 `shutdown` 确认退出。

默认后端保留后台任务记录直到插件停止，前台等待正常结束后释放记录。动作返回错误时停止该任务后续重复；任务 panic 不阻止其他任务的清理。Cron、固定频率补发、自动重试、持久化任务和并发配额尚未实现。

任务动作应观察 `signal.is_cancelled()` 或 `signal.cancelled().await`。期限依赖 Tokio 执行器仍能调度；阻塞系统调用或耗尽执行线程无法被 Tokio 强制终止，不应在异步动作中直接运行阻塞代码。默认 Kernel 被释放会请求取消任务，但只有显式停止才会等待退出并执行异步 Cleanup。

`TaskManager` 位于 `plugin-api/src/tasks.rs`，`TokioTaskManager` 为默认实现。替代后端的注册必须同步完成、不能同步执行插件动作；`run_foreground` 返回的 Future 只负责等待。`KernelServices` 新增 `tasks` 字段，结构体字面量可用 `..Default::default()` 补默认实现。任务测试通过注入替代后端验证插件 API 无需改变。

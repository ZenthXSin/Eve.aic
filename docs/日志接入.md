# 日志接入

插件通过 `PluginContext::log` 记录结构化日志。定义层不依赖 Tokio、tracing 或具体日志库；宿主通过 `KernelServices::logger` 选择实现，不注册进程全局 Logger。

## 插件记录日志

```rust
use eve_plugin_api::{LogEntry, LogLevel, PluginContext, PluginResult};

fn record(ctx: &PluginContext) -> PluginResult<()> {
    ctx.log(
        LogEntry::new(LogLevel::Info, "my-plugin.sync", "同步完成")?
            .with_field("items", "12")
            .with_field("source", "local"),
    )
}
```

| 类型 | 职责 |
| --- | --- |
| `LogLevel` | Trace、Debug、Info、Warn、Error，按严重程度递增 |
| `LogEntry` | 插件提供的目标、级别、消息与字符串字段 |
| `LogRecord` | 宿主生成的时间、插件来源，以及日志内容 |
| `Logger` | 可替换的 `log(record)` 和 `flush()` 后端接口 |

目标和字段名不能为空白；公开字段在投递时重新校验。重复字段键保留最后一个值。字段可承载任务 ID、业务标识等自定义信息；字段名即使叫 `plugin` 或 `timestamp` 也不会覆盖宿主元数据。当前字段值为字符串，暂不提供嵌套对象或跨进程序列化协议。

从 Context 投递时，时间使用当前 `SystemTime`，来源使用插件 Manifest 的 ID；不相信调用方自填的插件身份。宿主直接调用后端时可构造完整记录，这仍属于当前可信宿主边界。

## 选择实现

默认 `StderrLogger` 是 `WriterLogger<std::io::Stderr>`，输出 Info 及以上级别，每条日志占一行，包含 Unix 毫秒时间、来源、目标、消息与字段。字符串使用 Rust Debug 转义，保留中文并转义换行、引号和控制字符；此格式是可读文本，不是 JSON。写入和刷新错误返回 `PluginError::Log`；设备可能已经接收部分字节，失败不能回滚输出。

`WriterLogger::new(min_level, writer)` 可接入实现 `std::io::Write + Send` 的文件、缓冲流或自定义输出。一个 Logger 实例会锁住整条记录的写入；多个实例应由宿主协调共享输出。默认同步写入可能等待设备，高吞吐场景可实现队列型 Logger。

`MemoryLogger` 适合测试和宿主诊断，默认保存最近 1024 条 Info 及以上记录；可设置最小级别和正数条数上限。满后淘汰最旧记录，`snapshot()` 返回接收顺序的记录及淘汰计数，级别过滤不计入淘汰。上限限制记录条数，不限制单条内容字节数；日志不会随插件停止被删除。

```rust
use eve_kernel::{Kernel, KernelServices, backends::MemoryLogger};
use eve_plugin_api::LogLevel;
use std::sync::Arc;

let logger = Arc::new(MemoryLogger::new(LogLevel::Debug, 256)?);
let kernel = Kernel::with_services(KernelServices {
    logger: logger.clone(),
    ..KernelServices::default()
});
let snapshot = logger.snapshot()?;
```

实现自定义 `Logger` 后，直接替换 `logger` 字段即可；插件无需修改。自定义后端应校验记录、返回错误、实现刷新语义，并避免递归调用自身记录错误。Kernel 调用 Logger 前释放 Scope 锁，后端可访问 Context；若持有 Context，应遵守已有弱引用与资源生命周期约定。

## 错误与停止

日志调用成功表示已被接收或按级别过滤，不保证持久化。调用失败由插件决定是否传播；使用 `?` 会像其他能力错误一样影响当前动作，启动阶段传播会触发已有回滚。日志不属于启动事务，失败回滚不会撤回之前的记录。

已有任务可以在协作停止期间记录收尾日志。Scope 关闭后，旧 Context 以及 Cleanup 中捕获的 Context 均不能再投递；已经准入的同步投递可能与停止重叠，不会被强制中断。宿主应等待自己的并发调用结束后刷新。

宿主停止日志生产后调用 `Kernel::flush_logs()`，或者直接调用后端的 `flush()`；即使停止失败，也可以尝试刷新以保留诊断。`stop_all` 和 Drop 不会自动刷新，flush 也不等于文件 `fsync`。示例宿主在停止后显式刷新，若同时发生多个错误则优先返回原始业务错误。

## 实际验收

`cargo run -p eve-runtime` 输出消息处理、任务完成、预期启动回滚三条日志并刷新。Runtime 测试将同一批插件切换到内存实现，检查来源与业务字段。内核日志测试进一步验证过滤、容量淘汰、并发短写、控制字符转义、后端失败、Context 重入和停止边界。

当前日志能力面向插件显式记录。内核生命周期的自动诊断、调用链追踪、文件轮转、远程收集和持久化检索留待后续。

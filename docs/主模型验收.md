# 核心主模型多轮验收

本程序直接启动 `eve` 二进制，沿用 AGENT、普通配置、主模型（Chat/Responses）、Runtime、Session、Control 和 echo；不另装配一条演示链路。与离线 HTTP 测试共用验收流程。

## 运行

先在宿主环境配置 `EVE_OPENAI_API_KEY`；核心默认 deepseek-v4.1-flash / chat 和既有 API 根地址，可通过 `EVE_OPENAI_MODEL`、`EVE_OPENAI_PROTOCOL`、`EVE_OPENAI_BASE_URL` 替换。沿用[核心对话](./核心对话.md)的配置字段，reasoning_effort 普通配置默认空，核心 Chat 将空值映射为 none，Responses 空值不发送。可显式覆盖。新目录没有文件配置，因此本次使用默认与环境来源；不读取平日会话目录。

```powershell
cargo build -p eve-app --bin eve --locked
cargo run -p eve-app --example model_acceptance --locked -- ./.eve-model-check-001
```

`--eve <二进制路径>` 可指定已构建的入口，默认使用本示例构建目录旁的 eve；`--agent <身份文件>` 默认工作目录 AGENT.md。凭据、身份或二进制缺失时在创建验收目录前失败；模型与协议由核心配置选择，没有失败回退。既有记录使用 gpt-5.6-sol，只说明曾通过非流式单轮/工具验收，不表示本轮多轮已通过。

目录必须尚不存在，父目录须已存在；已有目录一律拒绝，原字节不改。每次验收使用新目录，不自动重跑失败的模型请求或工具。

## 实际检查

1. 首进程两轮：随机非敏感口令只在第一轮用户输入，要求一次 echo 执行并完整回复；第二轮要求从完成历史回忆口令，不调用工具。
2. 通过公开 FileStateStore 读取 Session 的字节文档，再用公开 SessionSnapshot 契约验证。首轮必须有恰好一组配对 echo 调用/成功结果，参数和值等于口令；两轮均 Completed，最终回复及控制台输出含口令，revision 为 4。
3. 首次 checkpoint 通过后，启动全新进程使用同一状态目录。第三轮输入不带口令，必须通过恢复历史回答；新轮次零工具，原两轮逐字段不变，revision 为 6。
4. 任一检查失败不启动后续恢复进程。首次两条输入是串行批量输入，首条 Provider 失败时核心可继续第二条已接收输入；这不重试原请求。Provider/协议错误、工具失败、伪造工具完成、缺失记忆或额外工具都会使验收失败。

标准成功路径为四次模型请求：首轮两次、后两轮各一次。异常模型若在回忆轮也调用工具，可能发生额外本地 echo 往返，最多六次请求；验收会失败。每个子进程期限按每轮最多两次 Provider 等待加 10 秒计算；期限到则回收进程并保留状态。强制回收可能留下 Pending，不能据此断言远端停止或没有工具副作用。

只显示并保存无正文/凭据的 JSON 报告，不把回复或原始错误体发布到终端/CI：

| 成功字段 | 值 |
| --- | --- |
| status | passed |
| first_process_turns / restored_turns / completed_turns | 2 / 2 / 3 |
| first_process_tool_calls / restart_tool_calls | 1 / 0 |
| revision_before / revision_after | 4 / 6 |
| reply_marker_verified / history_prefix_unchanged | true / true |

完整状态位于 `state/`；两进程的原始标准输出/诊断留在 `first.stdout`、`first.stderr`、`restart.stdout`、`restart.stderr`，失败不删除。它们可能包含身份和模型回复，供宿主本地诊断；验收口令不是密钥。根目录默认的 .eve 和 .eve-model-check-* 已忽略，不提交运行目录。

`acceptance.json` 通过临时文件同步和不覆盖发布生成；报告写入失败也返回非零，并保留原失败类别及 report_write_failed。必须同时核对进程退出码为 0 和本次报告 passed。报告不声明无法观测的远端请求次数、停止或模型质量。

# 状态持久化与进程恢复

目录锁通过独立的 RAII guard 持有：正常释放及读取快照失败时先显式解锁，再关闭文件。这样，进程创建过程中暂时继承或复制的文件描述不会把目录锁拖延到最后一个副本关闭。锁文件保留，不能删除后重建；保留状态文件的原子提交和错误语义。

`StateStore` 是定义层的字节键值接口。插件通过 `PluginContext::state_get` / `state_set` 访问自身命名空间；组合层可以选择内存、文件或独立的本地 PostgreSQL 后端，插件代码无需随存储方式改变。

`MemoryStateStore` 仍是默认后端，适合测试和临时状态。`FileStateStore` 将状态保存到本地目录，适合少量配置、检查点和恢复标记。

`eve-state-postgres` 提供本地 SQL 字节状态；`eve-cognition --database-config` 显式启用，未提供参数时继续使用文件后端。数据库配置、单宿主锁、状态目录绑定和测试入口见[PostgreSQL 状态](./PostgreSQL状态.md)。本文的原子替换及旧快照保留说明针对文件后端；SQL 提交报错存在结果未知的边界，不能直接套用文件写入的结论。

## 装配文件后端

```rust
use eve_kernel::{Kernel, KernelServices, backends::FileStateStore};
use eve_plugin_api::PluginResult;
use std::sync::Arc;

fn persistent_kernel() -> PluginResult<Kernel> {
    let store = FileStateStore::open("./data/state")?;
    Ok(Kernel::with_services(KernelServices {
        state: Arc::new(store),
        ..KernelServices::default()
    }))
}
```

打开后端会创建所需目录、将目录解析为绝对路径并取得独占锁。目录不能访问、锁被占用或状态文件不可读取时，返回 `PluginError::State`；组合层应报告错误，不要自动退回内存后端。

目录布局：

```text
data/state/
├── state.json       # 已提交的完整状态快照
├── state.lock       # 持锁文件，生命周期绑定 FileStateStore
└── <临时文件>        # 写入期间的候选快照，不作为恢复入口
```

`state.json` 使用版本化 JSON。例如 `demo.state-recovery` 插件的 `starts` 保存字节 `b"1"` 时：

```json
{
  "version": 1,
  "entries": {
    "demo.state-recovery": {
      "starts": [49]
    }
  }
}
```

命名空间取插件 ID，值保持原始字节。插件负责选择编码、校验数据和迁移自己的状态格式。宿主快照版本和插件数据版本是两个独立概念。

## 文件写入与失败语义

每次 `set` 都依次构造新快照、写同目录临时文件、同步文件内容，再原子替换 `state.json`，最后提交内存中的新值。成功返回后，后续读取和新进程打开后端都能读取本次提交。无需等插件停止，也没有额外的状态刷新调用。

如果写入、同步或替换失败，`set` 返回错误，当前后端内存中保留此前已提交的值。各次 `set` 在该后端内串行提交，避免并发更新互相覆盖其他键。

该接口只提供单次写入的提交边界，不提供多键事务；`get` 后再 `set` 也不是原子的读改写。计数器存在并发更新时，插件需要自行串行化，或注入具有额外事务能力的存储实现。

插件停止和启动失败都不会撤销已经成功写入的状态。恢复标记应表达业务中已经完成的步骤，不能假设插件启动失败会回滚状态。

## PostgreSQL 提交与未知结果

PostgreSQL 后端使用专用线程串行访问单个客户端，每次 `set` 在事务中提交单键写入。任意 SQL 操作失败会永久关闭当前后端，不自动重连、重试或退回其他存储；正常退出释放数据库内的 session advisory lock。接口仍同步等待，不提供跨插件事务。

提交响应失败时数据库可能已经写入。状态插件保留最后已确认的内存快照，并不证明数据库仍是旧快照；宿主应停止，下一次显式启动读取实际持久化状态。认知 Executing 恢复为 Blocked/Interrupted，Session Pending 恢复为 Interrupted，旧尝试不自动重放。完整边界见[提交失败与恢复](./PostgreSQL状态.md#提交失败与恢复)。

## 独占访问与损坏处理

- 同一目录同时只能打开一个遵守锁协议的 `FileStateStore`；同进程不同实例也需要遵守。要共享状态，可共享同一个 `Arc`，不能另开后端抢占目录。
- 锁随后端关闭或进程退出释放。`state.lock` 文件存在不代表锁正在被占用，不能靠删除锁文件解锁。
- 仅当 `state.json` 路径确实不存在时视为空库。快照须为普通文件，符号链接（含悬空链接）、空文件、JSON 损坏、未知快照版本和其他读取错误均拒绝打开，不会当成空库覆盖。
- 重启只读取 `state.json`。未完成提交的临时文件不参与恢复。
- 不支持运行中由外部程序改写快照或删除锁文件。独占锁约束使用同一锁协议的参与者，不是文件访问权限或插件沙箱。

遇到损坏，应先停止使用该目录的进程、保留文件进行诊断，再由运维恢复已知可用的备份。后端不自动修复或清空数据。

## 恢复的边界

恢复对象是按插件 ID 隔离的**字节状态**。进程重启后，宿主仍需注册和启动插件，插件在 `start` 中读取检查点并恢复自己的业务流程。

Future、执行中的任务、服务句柄、事件订阅及 `PluginContext` 都不属于快照。插件每次启动都应重新建立订阅、注册服务并按已保存的业务进度创建任务。状态恢复也不自动提供任务去重或恰好执行一次语义。

文件后端沿用当前同步 `StateStore` 接口，每次写入都会序列化完整快照并执行同步文件 I/O；大量状态或高频写入会阻塞调用线程。需要较大规模存储时，可通过同一抽象替换后端，异步访问或事务需求应另行定义明确契约。

临时文件内容会先同步，但当前实现不保证目录元数据在断电时已经持久化。因此，本阶段覆盖正常进程重启和文件替换原子性，不承诺掉电、硬件故障或所有网络文件系统上的持久性。重要状态仍需要独立备份策略。

## 两次独立进程验收

从项目根目录使用一个空目录，依次执行以下命令。每条命令都启动并退出一个独立 Runtime 进程，第二次必须使用同一目录。

```powershell
cargo run -p eve-runtime --example state_recovery -- ./target/state-recovery-demo
cargo run -p eve-runtime --example state_recovery -- ./target/state-recovery-demo
```

第一次输出：

```text
恢复前值：无；写入后值：1。
状态恢复验收通过。再次使用同一目录启动将读取本次写入值：./target/state-recovery-demo
```

第二次输出：

```text
恢复前值：1；写入后值：2。
状态恢复验收通过。再次使用同一目录启动将读取本次写入值：./target/state-recovery-demo
```

重复运行会继续增加计数。若需重新验收首次启动，选择另一个空目录即可。示例插件仅通过 `PluginContext` 读写状态，组合层在退出前停止插件并显式刷新日志；`flush_logs` 与状态写入无关。

# EVE.AIC 第一版架构设计

## 1. 总体分层

所有功能都先定义抽象契约，再提供独立实现。插件只依赖定义层，Runtime 负责选择和装配实现层。

```text
定义层：Plugin API、Trait、数据类型、错误和协议
                         ↓
实现层：Kernel、Event Bus、Service、State、Task、权限和日志实现
                         ↓
组合层：Runtime Host 选择实现并注册插件
```

分层规则：

- 定义层不依赖具体实现。
- 实现层实现定义层的 Trait，可以有多个实现。
- 组合层负责配置、替换和装配实现。
- 插件不能绕过 Context 访问实现层内部结构。

## 2. Plugin API

`plugin-api` 只定义插件可以看到的稳定契约：

- Plugin
- PluginManifest
- PluginContext
- PluginDependency
- ServiceId
- EventId
- StateHandle
- TaskId / TaskSpec / TaskSignal
- Permission
- PluginError
- RuntimeInspector / PluginStatus / PluginStopError（宿主只读诊断）
- RuntimeLifecycle / LifecycleRequest / LifecycleOperation（宿主生命周期控制）
- PluginFactory / PluginCatalog（组合层静态插件发现与创建）

插件不应依赖 `kernel` 的内部结构。`PluginManifest` 在注册前统一校验 SemVer 版本、依赖范围、自依赖和重复依赖；启动依赖前再次检查已注册版本。

## 3. 实现层与 Kernel

`kernel` 负责：

- Runtime 生命周期
- Plugin Registry
- 依赖图和启动顺序
- 插件状态机
- Context 创建
- Service Registry
- Event Bus
- State Store
- Task Manager
- Permission Checker
- 资源清理
- 错误和诊断

这些能力都应通过独立接口定义，再由 Kernel 提供默认实现。当前 `EventBus`、`ServiceRegistry`、`StateStore`、`PermissionChecker`、`TaskManager`、`Logger` 已在 `plugin-api` 定义，默认实现位于 `kernel::backends`，通过 `KernelServices` 装配。任务使用 Tokio 默认实现；日志提供输出流和内存两种实现，不依赖进程全局单例。状态提供默认内存后端与可选文件后端，插件接口保持不变。

任务扩展进一步分离行为与触发策略：插件实现 `Task` 定义带参数的新类型，实现 `TaskScheduler` 定义新的等待和调度规则；默认执行器通过统一契约管理这些对象，无需按业务类型增加分支。前后台模式与上述扩展组合，Scope、取消、错误报告和资源回收仍由内核统一负责。任务查询只保存 `TaskTypeId` 和 `TaskScheduleInfo` 等描述，不保留执行闭包。

## 4. Plugin 生命周期

```text
Registered
    ↓
WaitingDependencies
    ↓
Starting
    ↓
Active
    ↓
Stopping
    ↓
Stopped
```

启动失败进入 `Failed`。插件是否启用是配置，不单独作为生命周期状态。

## 5. Context 边界

插件只能通过 `PluginContext` 使用 Runtime 能力：

```text
PluginContext
├── emit / on：事件发布与订阅
├── provide_service / service：服务注册与获取
├── state_get / state_set：命名空间状态
├── check_permission：权限声明检查
├── spawn_task / run_foreground / tasks：任务创建、前台等待与查询
├── log：携带插件身份与时间的结构化日志
└── cleanup：异步资源清理
```

禁止插件获取 Runtime 内部可变结构。

宿主通过 `PluginRegistry` 注册和卸载插件，通过 `RuntimeInspector` 查询插件清单和任务，契约位于定义层。卸载与生命周期操作共用串行准入边界，只移除已完成收尾的注册表条目，不删除状态字节。查询不等待生命周期锁，可观察启动中和停止中的状态；清单是逐项快照。停止失败按插件与阶段汇总为 `PluginError::Shutdown`，退出检查失败不能返回停止成功。详见[运行时诊断](./运行时诊断.md)。

组合层可使用 `PluginCatalog` 登记可信静态 `PluginFactory`。目录保存经校验的清单快照，按 `(PluginId, Version)` 精确发现；允许同 ID 多版本共存，不自动选择版本或解析依赖。创建回调在目录锁外执行，实例清单必须与登记快照完全一致。目录不启动插件、不注册 Runtime 资源、不持久化工厂，宿主将创建结果交给 `PluginRegistry` 后再按 Kernel 生命周期运行。

宿主通过 `RuntimeLifecycle` 提交启动或停止操作、等待终态、查询和确认报告。准入后由独立执行任务持有操作，取消等待仍继续收尾；意外中断保留错误，不伪装成停止成功。该控制接口不注入插件 Context，详见[生命周期操作](./生命周期操作.md)。

插件注册与生命周期操作共用串行准入边界。启动或停止操作执行期间，`register` 会返回错误；操作完成后才能注册新插件，避免 `start_all` 或 `stop_all` 的插件快照遗漏并发注册。

以上为当前接口。插件只依赖 `plugin-api`，`example-plugins` 提供可执行的示例，`runtime` 负责装配。具体语义见[插件开发](./插件开发.md)和[日志接入](./日志接入.md)。

## 6. 第一版插件形式

第一版采用：

```text
Rust
单进程
静态编译
可信插件
Box<dyn Plugin>
```

暂不加载任意 Rust 动态库。未来的不可信或外部插件使用 WASM 或独立进程协议。

## 7. 最小认知组合边界（Issue #27）

可替换的认知能力通过插件接入，模型请求和工具调用循环由 Eve 宿主提供。职责边界如下：

| 能力 | 归属 | 约束 |
| --- | --- | --- |
| Memory、用户模型、Context、Cognition、Tools、Channels | 插件 | 通过公开 Service、Event 和任务契约协作，不访问 Kernel 私有结构 |
| 模型请求、响应处理和工具调用循环 | Eve 宿主 | 宿主选择 Provider；每次工具调用前校验插件状态、权限和参数 |
| 依赖预检、生命周期、Scope、资源收尾和失败报告 | Kernel | 沿用现有 Manifest、PluginRegistry 和 RuntimeLifecycle 语义 |
| 实现选择、配置和装配 | Runtime 组合层 | 选择可替换插件和宿主实现，将实例显式交给 Kernel 管理 |

首个闭环的最小装配路径是：

```text
通信通道输入
    ↓
Context / Cognition 插件提供动态快照
    ↓
Eve 宿主按固定布局组装并调用模型
    ↓
模型返回一个 Tool 调用批次
    ↓
宿主按并发策略校验并执行各 Tool
    ↓
工具结果回到模型，最终回复返回通信通道
```

Runtime 按固定布局放置规则、工具定义和输出格式；Context 只返回带版本的用户档案、相关记忆和会话历史等动态快照，本轮输入位于固定动态槽位。后台整理只能更新动态快照，不能改变固定前缀的顺序。插件依赖仍通过 Manifest 和公开 Service 解析，替换实现不改变宿主和 Kernel 的生命周期边界。

该路径是 Issue #27 的组合契约。当前仓库已实现其中的最小 Mock Provider、Context 和 Tool 宿主闭环；Memory、Cognition、Channel 的完整插件组合以及 Jev 实验继续按 Issue #24 的后续阶段推进。


### 7.1 Agent 提示词来源

Eve 的稳定 Agent 身份由显式选择的 `AGENT.md` 提供，与开发协作约定 `AGENTS.md` 分离。`eve-llm-api` 定义 SystemPromptSource/不可变快照，`eve-agent-prompt` 提供文本和本地文件实现，Runtime 通过 `LlmHostConfig.with_prompt_source` 装配一次并保存来源版本。原有直接 `system_prompt` 路径保持兼容，默认不扫描文件。

`AGENT.md` 只描述身份、能力范围、行为原则和动态议程边界，不授予工具权限、不承载密钥，也不替代 Runtime/Kernel 的权限、参数、生命周期和副作用校验。后续 `RULE.md`、`MEMORY.md`、自定义注入、`STATE`、`DRIVES` 和 `AGENDA` 通过组合层按作用域、优先级、版本和过期时间组成；动态内容不能重排或改写固定规则。

AGENT 来源的详细设计和交接清单见[AGENT.md 提示词设计](./AGENT提示词.md)。修改文件通过重新装配生效；在途请求不变，错误不得回退默认身份。身份不保存到会话历史，不因换身份重放工具。来源实现负责文件与哈希，Runtime 负责布局与 Provider 请求，Kernel 不理解 Markdown 语义。

## 8. LLM 调用契约与宿主边界（Issue #31）

最小 LLM 闭环使用独立的 `eve-llm-api` 定义 crate，而不向通用 `plugin-api` 加入厂商协议：

```text
eve-plugin-api        通用插件、服务、权限与生命周期契约
eve-llm-api           Provider、上下文、工具与消息契约
eve-kernel            生命周期、Scope、服务、权限和资源收尾
eve-runtime           LLM 宿主、显式绑定、超时与工具循环
```

`eve-llm-api` 依赖 `plugin-api`；`kernel` 不依赖 `eve-llm-api`。Runtime 选择可替换的 Provider，并以显式 `ToolBinding { name, service_id, expected_owner }` 将工具名绑定到插件服务。当前 Service Registry 不提供枚举，宿主不得扫描服务来发现工具。

Provider 只接收 Eve 内部的 `ModelRequest`，返回最终文本或一个有序 `ToolCall` 批次。Context 插件以 `ContextService(Arc<dyn ContextAssembler>)` 提供快照，工具插件以 `ToolService(Arc<dyn Tool>)` 提供定义、参数校验、并发策略和执行；包装类型使 trait object 能通过现有 Service Registry 注册。Memory、Profile 与 History 是 Context 快照的动态来源，不成为 Kernel 字段。

每次工具调用前，Runtime 必须核对工具名、调用 ID、参数对象、Service 所有者和插件 `Active` 状态，并用所有者清单执行既有权限检查。宿主复用 Kernel 装配时的服务、权限后端；仅新增 `RuntimeInspector::plugin_manifest` 只读清单查询。装配预检服务缺失是宿主配置错误，调用期服务不可用则回传失败 ToolResult，具体分类以[LLM 工具调用](./LLM工具调用.md)的错误表为准。

状态快照不构成执行租约。每轮开始前，相关插件必须已注册并处于 Active 状态；外层组合层可在两轮之间通过 Kernel 克隆管理插件。每次 `run_turn` 持有与各 Kernel 克隆共享的运行准入锁直到整轮结束；启动和停止等异步生命周期操作等待本轮完成，同步注册和卸载在本轮期间返回生命周期错误，取消整轮时释放本地准入锁。Provider 或工具不得在本轮中等待同一 Kernel 的生命周期操作，以免形成重入等待。工具 Future 由宿主直接等待，不自动归入 TaskManager。同一批次中显式并行安全的工具可在宿主并发上限内同时运行；同一串行作用域或未声明策略的本地 Future 按模型顺序互斥，单项结果按调用 ID 隔离并按原始顺序一一回传。每项工具有独立超时和协作式取消收尾窗口，不能承诺强制终止或回滚副作用，也不能将串行作用域解释为远端资源锁。`max_parallel_tool_calls` 默认值为 `10`，组合层从后续的配置服务取得已校验值并在每轮固定；配置服务本身的接口和自举由 #32 定义。固定指令来自宿主配置，Context 只返回版本化动态快照，排列不可由插件重排。上述 Mock 闭环及独立 OpenAI Responses 适配器已实现，非流式文本与工具往返已通过真实模型验收；会话恢复、流式输出和显式任务取消已通过本地验收。reasoning 续传、消息关系判断及自动重规划按后续 Issue 推进。

## 任务控制组合边界

公开控制契约由 eve-control-api 定义；eve-control-plugin 发布 ControlService，不依赖 Runtime 或厂商网络实现。宿主将 SessionControlRunner 通过 ControlRunner 契约传给插件，并显式声明上下文/工具和会话插件依赖。通道使用 submit/cancel/wait/snapshot/accepts，不解析 SessionLlmHost 私有类型。实际 LLM 与工具循环仍由内置宿主实现。

生成 Future 和取消信号由控制器持有，用户仅取消等待控制结果不会取消执行；显式 cancel 关闭本代事件流，由宿主完成工具析构和失败提交。代际过滤、终态与 Pending 阻止替代规则见[任务控制](./任务控制.md)。

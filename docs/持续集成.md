# 持续集成

工作流定义在 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)，通过 GitHub Actions 验证 Rust 工程和实际运行示例。

## 触发与权限

- 任何目标分支的 PR 都触发检查，包括以另一个功能分支为基础的依赖 PR。
- `main` 收到推送时重新检查；支持在 Actions 页面手动运行。
- 工作流只申请 `contents: read` 权限，检出代码后不保存凭据；不发布构建、不部署服务、不合并 PR。
- 同一工作流和分支或 PR 有新运行时，取消尚未完成的旧运行。
- Stable 的 Ubuntu 任务限时 40 分钟，最低 Rust 版本任务限时 45 分钟；两项独立执行。

工作流在 PR 中可供审查，不代表已合并进入默认分支。实际是否触发、是否通过，以对应提交的 Actions 记录为准。此配置也不会自动启用分支保护或“必须通过检查才能合并”的仓库规则。

## 平台与 Rust 版本

Windows CI 已停止，历史运行结果保留。持续集成覆盖 Ubuntu；发行另在 Linux x64 与 ARM64 原生环境构建和验收，见[发行说明](./跨平台发行.md)。

| 任务 | 环境 | 检查范围 |
| --- | --- | --- |
| Stable | `ubuntu-latest` | 格式、全目标编译、Clippy、测试、协作示例、跨进程恢复示例 |
| 最低支持版本 | Ubuntu，Rust `1.95.0` | 原文件来源校验、锁定依赖的全目标编译、模型和会话定向回归、受影响包的严格 Clippy |

Stable 通过 `rustup` 安装当前稳定版及 `rustfmt`、`clippy`。最低版本检查与工作区声明的 `rust-version = "1.95"` 对应，用于发现新语法、标准库接口或依赖对最低版本的影响；它不替代 Stable 的完整测试。

最低版本任务先校验 Codex 原文件，再安装并记录实际 Rust/Cargo 1.95.0 版本。全部目标编译成功后，分别运行公共会话契约、原 Codex TCP/SSE、旧 OpenAI Chat/Responses、主辅九组合、切换入口、Runtime 会话持久化和请求恢复测试，并对适配器及受影响宿主包启用 `-D warnings`。独立回归步骤继续收集失败，任何失败仍使任务失败。Stable 和最低版本任务都关闭 dev/test 调试信息与增量编译，限制冷构建的磁盘占用。

QQ 和独立 Web 的 4 个新适配器进程用例由 [QQBot 通道工作流](../.github/workflows/qqbot.yml) 使用实际 1.95.0 编译的宿主运行；同一任务也执行 1.95 格式检查。最低版本任务不重复启动这套进程，新增的 Stable 适配器进程验收仅在 Linux 运行。验收覆盖必须关联同一提交的两个工作流结果，不能把已接入 CI 写成已运行通过。

Rust 1.95 是保留原 Codex workspace 所需的统一最低版本；原依赖清单不改写降版。格式命令在 Eve 根目录运行 `cargo fmt -- --check`，避免 `--all` 递归格式化外部 path dependencies。Stable 的构建、Clippy 和测试仍覆盖整个工作区，原文件另由 `python3 scripts/verify-codex-upstream.py` 校验。切换后的锁文件解析、真实 metadata/格式 target 覆盖清单与 1.95 运行结果必须独立记录，既有 1.89 或当前 Stable 成功记录不能替代。

仅使用官方 `actions/checkout`，固定为经 GitHub API 核实的 v7.0.1 提交 `3d3c42e5aac5ba805825da76410c181273ba90b1`。该版本使用 Node.js 24，要求 Actions Runner 至少为 2.327.1；当前采用 GitHub 托管的 `latest` 镜像。Rust 工具链直接由 `rustup` 安装，不依赖额外第三方安装或缓存 Action。

## 检查命令

在项目根目录执行：

```bash
cargo fmt -- --check
cargo check --workspace --all-targets --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo run -p eve-runtime --locked
cargo run -p eve-runtime --example lifecycle_operations --locked
```

`--locked` 要求沿用仓库中的 `Cargo.lock`，不能在检查时隐式修改依赖解析结果。格式检查不改写文件，Clippy 将警告视为失败。

最低版本可在本地另外检查：

```bash
rustup toolchain install 1.95.0 --profile minimal --component clippy
rustc +1.95.0 --version --verbose
cargo +1.95.0 --version
python3 scripts/verify-codex-upstream.py
cargo +1.95.0 check --workspace --all-targets --locked
cargo +1.95.0 test -p eve-llm-api --lib --locked
cargo +1.95.0 test -p eve-llm-codex --lib --test responses --locked
cargo +1.95.0 tree -p eve-llm-openai -e features -i serde_json --locked
cargo +1.95.0 test -p eve-llm-openai --locked
cargo +1.95.0 test -p eve-app --lib models::tests --locked
cargo +1.95.0 test -p eve-app --lib qq_model --locked
cargo +1.95.0 test -p eve-runtime --test llm_host --test session_host --test session_http --test model_resolver --test context_compaction --test openai_provider --test streaming --locked
cargo +1.95.0 clippy -p eve-llm-api -p eve-llm-openai -p eve-llm-codex -p eve-runtime -p eve-app -p eve-developer-tools -p eve-web-panel-api --all-targets --locked -- -D warnings
```

## 实际运行与持久化验收

协作示例验证插件依赖、事件和服务交互、前后台任务、自定义任务与调度、日志、失败回滚和只读诊断。

生命周期操作示例暂停一次 Cleanup，主动令宿主等待超时，再放行并重新等待。它核验操作继续、实际清理完成、结果可重复查询及显式确认释放记录；Ubuntu 运行该示例。

恢复示例在每个平台的 `RUNNER_TEMP` 下使用同一临时目录，先后启动两个独立进程。CI 检查退出码，并精确断言首行输出：

```text
恢复前值：无；写入后值：1。
恢复前值：1；写入后值：2。
```

每个进程退出后还读取实际 `state.json`，断言快照版本为 `1`，且 `entries["demo.state-recovery"]["starts"]` 分别严格为字节数组 `[49]`、`[50]`，即 UTF-8 文本 `1`、`2`。缺少文件、JSON 无效、字段类型或内容不符都会使检查失败，不能仅凭终端输出判定恢复成功。

第一个进程退出后，第二个进程必须从磁盘恢复计数。目录包含运行 ID 和重试次数，不与旧运行复用；两个示例进程之间保留该目录，不用删除状态来绕过恢复检查。Ubuntu 使用 PowerShell 7 脚本执行现有恢复断言。

持久化测试还会实际建立跨进程文件锁，验证占用期间拒绝打开、释放后可重新打开，以及写入失败和损坏快照不被静默清空。符号链接测试会创建有效及悬空的 `state.json` 链接，确认拒绝打开且链接与目标保持不变。创建链接失败会使测试失败，不会跳过后声称通过。

这些检查覆盖当前文件后端的正常进程恢复和文件系统行为，不证明断电、硬件故障或网络文件系统上的持久性。具体提交、锁和恢复语义见 [状态持久化](状态持久化.md)。


## OpenAI 离线 HTTP 验收

Stable 的 Ubuntu 任务运行 `openai_offline` 示例，与手动真实示例共用文本/工具 smoke test 流程，验证 3 次真实 loopback HTTP 请求、Bearer 虚构凭据、插件工具执行、调用 ID 和结果回传。格式和全目标检查也编译手动真实示例；CI 不运行它，不读取真实 Key，不调用外部模型。

`cargo test --workspace --locked` 同时覆盖响应转换、本地 HTTP 和 Runtime 组合测试。真实文本与工具闭环已在 2026-09-30 手动验收；CI 不替代真实模型兼容性检查，会话多轮真实 API 验收仍后置。


## 会话独立进程验收

Stable 在 Ubuntu 连续运行四个 session_recovery 进程：完成一次工具轮次、重启继续、留下 Pending、重启后明确新请求。脚本验证旧工具执行数为 0、历史消息数依次为 0/4/6/6，以及第四次有一个 Interrupted；随后解析 state.json 的 sessions.v1 字节文档，核验版本 1、会话 revision 8、四轮记录和第一轮完整工具消息。

工作区测试另外覆盖文件重建后的 Responses HTTP 请求格式、调用 ID/失败结果/final_answer、稳定前缀、不同会话并行、保存/取消失败及生命周期等待最终写入与工具析构。坏状态测试检查原文件不变。细节见[会话恢复](./会话恢复.md)。

流式节点新增 streaming_offline 的 loopback SSE → 工具 → 会话验收，并以 session_recovery 的 --stream / --cancel-stream 四次独立进程检查历史长度、保存通知、Failed/Cancelled 磁盘记录及旧工具零重放。

## 任务控制独立进程验收

Ubuntu Stable 运行 controlled_session 两次，验证部分回复 → 显式取消 → 新任务工具往返；检查每次模型请求 3、工具执行 1、保存通知 1、旧事件接受 false。第二次读取已完成工具历史，旧工具不重放；完成消息 4/8、turn_id 2/4，磁盘 revision 8，第一/第三轮 Failed/Cancelled、第二/第四轮完整工具历史各 4 条。Rust 1.95 编译公开控制契约、插件、组合层及全部目标。


## 消息关系独立进程验收

Ubuntu Stable 连续运行 message_relations 两次，检查模糊消息只澄清、两项原文意图触发同任务重规划、旧事件被过滤以及每进程只执行一次工具。除报告历史 4/8 和 turn_id 2/4 外，还解析 state.json 的实际会话文档：revision 8，第一/第三轮 Failed/Cancelled，第二/第四轮完整工具历史，修订 JSON 保留基准“旧任务”及补充/纠正原文。Rust 1.95 检查全部新契约、插件、示例和测试编译。

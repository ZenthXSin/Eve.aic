# 编程子代理与思考强度

Eve 按实际复杂度决定分工。简单任务直接完成，不使用子代理，包括明确的源码查询、局部代码与 API 解释、小范围修改和简单验证；中等偏上、需要持续多步实现与验证的编程任务，如跨模块改动或复杂故障定位，交给内置 `coding` 子代理。复杂度由 Eve 结合当前上下文判断，不仅凭编程关键词、用户消息长短或文件数量，也不额外调用模型做分级。简单任务推进中变复杂时，可以交接已有结果后再委派，不从头重做。委派后 Eve 负责理解需求、交接上下文、沟通进展、判断结果和保存经验。子代理沿用同一个 Eve 的身份、当前用户范围及已有授权；角色名称不产生另一套人格。

主会话实际提供 `run_subagent` 时，使用 `agent_id="coding"`。通常显式设置 `include_context=true`，并在 `task` 中补齐当前问题、工作区、已有改动、已经取得的日志和结果、文件分工及需要核验的结果。`include_context` 的工具默认值仍为 `false`；提示要求在编程委派时主动选择携带。快照保留派发前当前模型可见的历史，不会自动读取窗口外原文，也不会执行历史中的工具调用。完整边界见[任务上下文与恢复](./任务上下文与恢复.md)。

coding 使用宿主实际装配的普通工具完成委派，不再递归派发。独立工作可以并行，有依赖的工作接续真实结果，同一文件应有明确执行者。工具未装配或调用失败时按实际回执处理，不能虚构“已经交给子代理”。主线程收到结果后判断证据是否支持结论，后续简单核对或收尾可直接完成，仍属中等偏上的编程工作再交给 coding；无需重复已有充分证据的验证。

子代理返回实际改动、已经运行的验证及回执、未确认的事项，以及可复用经验的来源和适用条件。派发成功、得到总结、编译通过和实际运行成功分别表明不同进展。子代理无法写持久轮次记忆时，由主线程依据真实回执调用已有记忆、经验或便笺能力保存；只有提交成功才能说已保存。记录进度不自动触发播报，不固定要求开头确认、中途汇报或结尾总结，也不为播报或整理额外调用主模型。

## 编程模型的选择

内置 `coding` 使用独立模型用途 `coding`，默认继续使用 `primary`。这让编程路由可以单独配置，并不表示上线后自动拥有两种不同模型。应先取得用户选择的准确编程模型名称、端点与凭据配置，再把该用途切到已配置的辅助角色；在真实请求验证前，不能声称独立编程模型已经可用。

本次编程角色的配置目标为 `gpt-6-astra`、思考强度 `high` 和独立凭据，实际生效以宿主配置及真实请求回执为准。密钥由宿主管理，不写入源码或文档。

| 配置 | 含义 |
| --- | --- |
| `runtime.model_uses.coding_role` | `primary` 或 `auxiliary_small`，默认 `primary` |
| `runtime.model_uses.coding_max_output_tokens` | 非零时覆盖编程用途输出上限，`0` 继承所选角色 |
| `runtime.models.auxiliary_small_*` | 辅助角色的启用、提供方、模型、期限、输出上限与凭据引用 |
| `provider.openai.auxiliary_base_url`、`auxiliary_protocol` | 可选的独立辅助端点与协议 |
| `provider.openai.auxiliary_reasoning_effort` | 默认空；空或 `inherit` 继承全局，显式值覆盖辅助角色的思考强度 |

独立强度也可通过 `EVE_OPENAI_AUXILIARY_REASONING_EFFORT` 配置，文件覆盖优先于环境值。`coding_role=auxiliary_small` 且辅助强度设为 `high` 时，主角色继续采用全局强度；随后使用 `/effort default` 不会清除辅助角色的 `high`。该覆盖属于辅助角色，其他选用同一角色的用途也采用它；它不根据任务文字选择强度。辅助强度设为 `omit` 表示独立省略参数，设为空或 `inherit` 才恢复继承。

辅助角色提供方可选 `openai` 或 `codex`；前者支持 Chat/Responses，后者使用 Responses。当前通用 `openai` Responses 解析仅支持最终文本或函数调用；编程模型返回 reasoning 或 commentary 时，应使用已经支持这些事件的 `codex` 适配器。它只忽略同一 reasoning 项重新封装后的不透明密文差异，仍核对项身份、思考摘要、最终正文与工具调用，不能把思考内容当作用户回复。端点、协议与引用须符合宿主配置，具体设置见[模型配置](./模型配置.md)。只给角色起名“编码”不会改变路由：内置 `agent_id="coding"` 才选择 `coding` 用途，其他角色沿各自已有用途。明确选中的辅助配置无效时返回真实错误，不回退主模型冒充成功。

coding 单次模型请求期限由所选角色的 `runtime.models.auxiliary_small_timeout_ms` 控制，主会话的流式期限不会自动覆盖它。高思考强度请求可能在 30 秒后才返回首包，应按实际响应时间配置；本次部署使用 120000 毫秒。超时失败不能因文件已经修改就声称完成，也不能自动重放已经执行的工具。

主会话和子代理沿用共享步数、原期限、取消与并发规则，模型分工不增加额度。每次执行捕获所选配置，后续配置变更不替换在途模型。子代理调用和真实结果仍由原调用方记录；已完成工作不因重启重新执行，调用结果未知时先核对原回执。持久化、旧记录兼容和回退边界沿[子代理角色与共享预算](./子代理角色与共享预算.md)。

## `/effort` 命令

QQ 中发送 `/effort` 查看当前值和可选档位，不调用模型探测；普通成员也可查询。主人或管理员可以全局修改并持久保存：

```text
/effort
/effort high
/effort default
```

可选值来自命令实际校验：`default`、`none`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`。`default` 在配置中保存为 `omit`，命令也兼容直接输入 `/effort omit`。`default`/`omit` 表示不传思考强度参数，`none` 则仍显式传参；供应商是否支持具体值以实际请求为准。未显式配置时默认不传，原有显式配置和环境值继续保留。

修改写入全局 `provider.openai.reasoning_effort`，影响主角色及继承全局强度的用途，不是只对当前用户生效；不会覆盖显式设置的 `provider.openai.auxiliary_reasoning_effort`。因此 coding 使用主角色或辅助角色继承全局时随命令变化，辅助角色独立设为 `high` 时保持 `high`。配置提交沿既有 CAS、备份与恢复机制，重启后保留；新一轮及后续解析采用新值，已经捕获配置的主会话、后台任务和子代理继续原快照。自然语言修改仍可使用 `set_reasoning_effort`，工具中的省略值为 `omit`。

成功回执例如“思考强度已设为：high。已保存，新一轮生效；在途请求继续使用原配置。”只证明保存成功。命令不改变模型、输出上限、工具步数或自主额度，不增加 `temperature`，也不自动探测或为不支持的档位静默降级。无效参数不写配置，修改身份沿宿主可信主人/管理员绑定。

# 自升级申请与诊断

> 2026-11-13：生产已改为直接替换升级和第三方 QQ SDK，当前机制见[直接替换与完整日志](./直接替换与完整日志.md)。下文保留之前版本的实现记录。

Eve 提交已完成的 Git 提交后，可直接申请：

```ts
return await tools.upgrades.request({ commit: "完整的40位Git提交" });
```

申请是异步的。后续用 `tools.upgrades.status()` 查询最近一次申请，不必保存或手抄长申请编号；要查指定历史申请时，仍可使用 `tools.upgrades.status({ actionId })`。查询需要当前在线实例的真实所有权证明，旧实例、过期实例与任意脚本不能借查询取得监督管理权限。

回执的 `state: submitted` 只说明进入了监督流程。`outcome: confirmed` 才说明旧 Eve 已明确接受新版。准备时可看到 `phase` 和 `operation`；发生失败时会返回 `reason` 及 `failure` 中的阶段、具体操作、错误种类和有界说明，不包含控制密钥或完整异常堆栈。准备构建失败的回执同样保留诊断。遇到未知/超时应先查原申请，不重新制造申请碰运气。

观察快照使用执行服务的 `timeline.page`，每页最多 128 条，仍受 12 MB 累计字节上限约束，单条较大的原件单独返回。3387 条小记录由 424 次串行读取减少为 27 次。旧实例照常验证每条来源链与最终游标，准备读取期间持续续租；记录摘要 `records.page` 和管理面板自有分页维持原来的每页 8 条。

固定源码机械校验、候选独立身份、出口代际隔离、健康检查、旧 Eve 明确确认和自动回切继续生效。优化读取与诊断不延长既定确认期限，不会默认接受新版。

部署时执行服务与监督服务需要更新固定源码路径；先更新执行服务即可让旧实例受益于观察分页加速。监督更新提供具体阶段/失败信息，实例正常升级后提供无编号查询的客户端支持。不能直接修改正在运行的固定 release，不能在交接进行中重启监督器；生产更新须按现有受控暂停、排空、恢复与健康核对流程实施。

## 宿主明确发起升级

宿主可在已有 `/supervisor` 独立控制密钥鉴权下发送：

```json
{ "method": "requestUpgrade", "args": { "commit": "完整的40位Git提交", "requestId": "稳定的短申请编号" } }
```

`requestId` 限 1 至 64 个英文字母、数字、下划线、点、冒号或连字符；同编号重试沿用原回执，同编号换提交被拒绝。回执 `actionId` 使用 `administrator_` 前缀，持久记录 `requestedBy: "administrator"`；这明确表示宿主发起，不能称为 Eve 自主申请。既有实例申请记录为 `requestedBy: "instance"`，更早未记录来源的回执按 instance 理解。

该入口使用独立监督控制密钥，不使用管理面板会话、守护密钥或伪造 Eve 的实例证明。实例 `/upgrade` 不能传管理标记、抢占管理员编号或取得控制密钥。管理员申请仍复用原源码验证、候选隔离、健康检查与真实旧 Eve 明确确认；有升级或持久暂停时不会新增另一申请。没有新增网页按钮或脚本管理能力。

# Debian 12 生产构建

`debian12-release.yml` 为固定源码提供独立的 Linux x64 生产产物。构建使用官方 `rust:1.95.0-bookworm` 的固定 amd64 digest，匹配 Debian 12、glibc 2.36；Node 固定 22.22.0 并验证官方压缩包摘要。现有 Linux x64/ARM64 便携发行验收继续独立运行。

先收齐准确组合提交的 CI，核对 PR 头和实际检出树，再显式启动一次生产构建。工作流进入主线后可手动输入完整 40 位 `source_revision`。工作流尚在同仓 PR 时，添加 `debian12-<完整 40 位 head SHA>` 标签触发；分支更新不会自动重跑该大构建，旧 SHA 的标签也不会构建新头。GitHub 要求 `workflow_dispatch` 工作流先位于默认分支，因此保留这一首次验收入口。[GitHub 官方说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)

仅构建 `eve-qqbot`、`eve-web`、`eve-memory`，使用 `--release --locked`，不改 Cargo.lock、不启用本机 CPU 指令，也不上传 target 或依赖缓存。原 Codex 文件逐个校验；构建、验收、打包三个阶段均验证源码未改变。产物记录源码提交与 tree、依赖锁和原文件清单摘要、工具链与镜像、每个二进制的大小和摘要、ELF 架构、全部动态库和版本符号。

18 组进程验收使用实际发布二进制，覆盖 QQ/Web 适配器切换、会话与身份、缓存统计、请求阶段诊断、普通工具免审、原文范围、自由探索、后回复、归档、压缩和升级恢复；记忆容量组通过同目录 `eve-memory` 实际读取逐块归档。另有两组 Python 宿主恢复夹具，验证监督器和固定宿主契约，不冒充 Rust 二进制验收。三个二进制也分别验证帮助入口和 ELF 兼容性。模型与 QQ 均为本地替身，不连接生产。

容器需要真实命名空间权限；先验证 bubblewrap，再运行原用例，保留用例期限和断言。普通断言失败后继续收集其它独立组，最终整体失败且不生成发布包。若整组超时，Python 无法保证派生监督器均已退出，立即终止后续验收并让失败作业的容器收尾，防止残留进程影响其它组。

成功产物包含三个二进制的压缩包、`provenance.json` 和 `SHA256SUMS`；另存原始日志。下载时核对 GitHub run/artifact 身份、官方摘要、源码及 tree、全部记录和解包后二进制摘要。远端动态库检查证明固定构建镜像中的兼容性；构建镜像包含开发依赖，不能因此声称所有干净 Debian 12 主机都已具备这些动态库。部署前还需把 `elf.json` 的实际 SONAME 与目标宿主环境逐项核对，并在宿主隔离目录运行帮助入口和真实进程预演。

该流程只构建与验收，不部署；生产切换还必须通过当前状态四阶段预演和候选首次启动前故障的恢复路径，并保留当前记忆、经历和未知回执。

新增入口需远端实际执行通过后才构成 Debian 12 可运行证据。本地静态核对、其它 Ubuntu CI、旧版二进制兼容测试均不能替代该结果。

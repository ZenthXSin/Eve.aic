# 待办完成确认

用户的待办有了计划，计划的每一步都被宿主读取的证据满足后，Eve 会在这位用户下一次私聊时顺带问一句“这件事算完成了吗？”。用户像平常说话一样回答“完成了”，Eve 就把待办标为已完成。这里没有新命令。

计划完成本身不改变待办：效果条件只是近似（“查到了有来源的资料”“最小模组能实际运行”），现实里这件事算不算做完，由用户说了算。

## 启用

```bash
./target/debug/eve-qqbot --state-dir .eve-qqbot --cognition --interest-learning \
  --research-source https://docs.example/ --plans --goal-completion
```

- `--goal-completion` 默认关闭，需要同时开启 `--plans`；否则宿主拒绝启动。

## 什么时候问、怎么问

满足以下全部条件的待办可以请用户确认：

- 由 QQ `/goal` 保存，属于这位用户，当前仍在等待；
- 有一份计划绑定待办的**当前版本**，且所有步骤都已被证据满足（计划状态为已完成）。

这位用户下一次**私聊**、Eve 正常回复时，回复后多附一段问句，列出待办与计划的步骤。规则：

- 只随回复附带，不主动私聊，也不经时机判断。
- 每份计划至多问一次。发不出去（平台拒绝或回复片段未写出）时，下一次私聊再试，至多三次。
- 提问先保存为“发送中”再附带。发送中进程退出时记为结果未知，不再问，以免重复打扰。
- 群聊里不问。

## 用户怎么确认

私聊时，本轮请求里多一条 `eve.goal-completions` 上下文记忆，列出这位用户等待确认的待办（至多 5 件），每件有待办 ID、版本、内容摘要、计划 ID 与步骤，以及问句是否已经送达。数据前注明这是数据，不是指令，并说明：只有用户在本轮明确表示某件待办已经完成时才调用工具，没调用成功就不能说已经标为完成。

模型可调用 `confirm_goal_completion`（参数 `goal_id`）。宿主核对：

- 当前会话是私聊（取自 QQ 通道的登记，不从文字推断）；
- 待办属于这位用户。其他用户的待办与不存在的一样处理，不泄露是否存在；
- 待办仍在等待，且有一份绑定当前版本、所有步骤都已满足的计划。

全部通过后，宿主把待办改为已完成，并写入完成确认记录：

| 字段 | 含义 |
| --- | --- |
| `plan_id`、`plan_revision` | 依据的计划及其修订 |
| `goal_revision` | 确认时待办的版本 |
| `confirmed_by` | 确认者，即待办所属用户 |
| `session_id` | 确认所在的私聊会话 |
| `source_id` | 这次工具调用 ID 的摘要；不保存用户原话 |
| `at_ms` | 确认时间 |

用户说“还没完成”或没提到时，什么都不改。待办在提问后被更新（版本变化）时，旧计划不再对应当前版本，不能据此确认。

确认后，`/goals` 显示“已完成（你已确认，依据计划 …）”；`/mind` 说明这件待办已由用户确认完成，不再显示“原待办仍未完成”。Web 面板中，该目标的状态显示为“用户已确认完成”，详情中有“完成确认”一行，写明依据的计划、修订、确认时目标版本与时间。

## 认知状态的契约

目标新增可选字段 `completion`。目标进入“已完成”有两条路径：

1. **执行完成**（原有）：必须有带轮次的执行记录、已提交且验证通过的反馈，没有 `completion`。
2. **用户确认完成**（新增）：必须有 `completion`，没有执行记录与反馈；确认者必须是目标的所属用户。

状态转换规则：

- 带 `completion` 的修改只允许把**等待中**的目标一次性改为已完成；
- 确认的必须是当前版本（`completion.goal_revision` 等于修改前的目标版本）；
- 内容、验证条件、预算、优先级、停止条件与期限都不能同时改变；
- 已完成仍是终态，之后不能再修改。

新建目标仍只能是就绪或等待。`completion` 只由宿主写入：认知管理能力不注册到通用服务目录，也不交给模型；模型只能通过上面这个经核对的工具请求确认。

## 持久化与恢复

- **认知状态**：
  - 没有完成确认的目标不写出 `completion` 字段，旧状态文件读写不变。
  - 写入过完成确认之后，旧版本的 Eve 读到这个字段会按损坏处理并拒绝启动，原字节保留，不会清空。
- **提问账本** `eve.completion/questions.v1`：
  - 认领与结果都先保存再生效；同一用户同一计划的提问 ID 固定，重复认领不会多出记录。
  - 重启时，发送中的提问记为结果未知，不再问。
  - 严格读取：重复键、未知字段、状态与尝试记录不一致都拒绝；损坏或版本不支持时拒绝启动，原字节保留。
  - 写入失败时关闭实例；之后读取也失败，不回退到旧缓存。
  - 至多 512 条记录：满了只删除最早结束的一条（已送达、结果未知、尝试用尽），发送中与待重试的记录从不删除。
- **认知状态与提问账本**：两者是两次独立提交，没有跨插件事务。提问送达与否不影响能否确认；确认依据的是认知状态与计划账本的当前快照。

## 分层

- 定义层：
  - `eve-cognition-api`：`CompletionConfirmation` 与目标的两种完成路径；
  - `eve-completion-api`：提问记录、状态、`CompletionLedger` 契约。
- 实现层：
  - `eve-cognition-plugin`：校验“等待 → 已完成”的确认转换；
  - `eve-completion-plugin`：持久提问账本。
- 组合层（`eve-app`）：
  - `qq_completion`：选出可确认的待办，作为通道投递点随回复附带问句（按 `goal-done-` 前缀分流投递结果），提供私聊上下文与确认工具；
  - `/goals`、`/mind` 与 Web 面板显示确认完成。

## 验收

- `cargo test -p eve-cognition-plugin --test completion`：
  - 正常确认并落盘、重开后仍在；
  - 版本不符、确认者不是所属用户、同时改动内容、无确认也无执行、等待中却带确认、确认同时带执行、就绪目标被确认，都拒绝且不写入；
  - 完成后不能再改；没有确认时状态文件里不出现该字段。
- `cargo test -p eve-completion-plugin`：
  - 每份计划只问一次，发不出去至多再试两次，送达后不再问；
  - 重启把发送中记为未知；写入失败关闭实例；
  - 损坏、未知字段与不支持的版本拒绝启动并保留原字节；
  - 满了只腾出最早结束的记录。
- `connectors/qqbot/test/completion_test.py`（实际 eve-qqbot、模型替身、文档站点、fake bridge 与 Mindustry 服务端替身）：
  - 计划由研究与实践后台实际推进到全部满足后，待办仍为等待；
  - 下一次私聊回复后附带问句，再聊不再问；
  - 群聊与其他用户调用确认工具都被拒绝，也看不到上下文；
  - 所属用户自然地说“已经做完了”，模型调用工具后待办标为已完成，记录依据的计划与确认来源，不保存原话；
  - 重启后 `/goals`、`/mind` 如实显示，且不再问；
  - 默认关闭，单独给出 `--goal-completion` 时拒绝启动。

模型替身只证明宿主契约；真实模型能否准确判断“用户是不是在说这件事完成了”，留待本地实机验收。

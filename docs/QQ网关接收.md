# 独立 QQ 网关接收

本机真实探针已在约 405 毫秒内到达 Ready 并持久化恢复态，没有收到消息、发送 QQ 或调用模型。
保留首次地址拒绝与后续限时未就绪证据；后者当时缺少阶段观测，不据此归因为平台鉴权故障。
现有输出已区分连接、Hello 与 Ready，避免仅凭 connecting 判断卡在哪一层。

这批在入站日志上接官方网关、连接监督和持久恢复序号，仍不调用模型、不运行 Eve 意识流，
也不发送 QQ 聊天。主人已授权贯通后上线测试并只回私信，本批只是贯通的一步。

## 接收与水位

`QqClient.openGateway()` 取得 `/gateway/bot` 返回的接入点，用当前 AccessToken 完成
Identify 或 Resume。访问凭据只在适配器对象/连接闭包中，不作为普通接口返回、不写日志。
正式连接要求 wss，只有本机回归允许 ws；接入点只接受配置 API 的主机或当前实测官方旧网关
`api.sgroup.qq.com`（仅在 API 为 `api.bot.qq.com` 时允许），避免将鉴权 token 写给第三方。
文档示例与本账号的真实返回不同；首次拒绝的证据保留，实际返回已脱敏记录并显式兼容。

`QqGateway` 按 Hello 给出的周期发送心跳，无 ACK 则断开并退避恢复，不依赖模型。Identify
使用 `QQBot AccessToken` 与明确 intents；本接收器选择 C2C 的 `1<<25`，此订阅可能也带群事件。
发送范围与订阅分开，测试配置只能生成 private 发送组件。

事件按接收顺序串行交给 `onDispatch`。消费回调完成后才保存 session/sequence，保存成功才
作为恢复水位；Ready 同样经过回调与持久化。重复序号不重复调用消费者。RESUMED 即使序号
等于原水位也确认连接就绪，但不假装出现新消息。心跳一直使用已保存的序号，不跨越慢消费。

队列最多暂留 64 个事件，积压时停收并断开，等已接受事件保存后从最后水位恢复补发。此上限
是连接缓冲，不是丢弃用户记录的条数；未接受的事件不能推进 s。若平台恢复窗口已失效，旧窗口
内未补发消息的完整性仍不能保证，本批没有平台历史补拉能力。

处理器/水位保存失败是本地致命错误，停止当前接收并保留现场；不偷换成自动跳过或重新 Identify。
服务器明确 InvalidSession 或旧水位无效时，先清持久恢复态再鉴权。没有权限、封禁、协议配置
错误停止连接；暂时断线退避重连。取消不再接收新事件，但等待已经开始的保存完成，失败仍报告。

## 独立接收器

`QqReceiver` 在数据目录取得排他文件锁，再启动网关和入站日志。第二个同目录实例被拒绝，
不能同时更新水位或入站记录；锁随退出释放。此锁覆盖本接收器，不代替企划案中守护管理的
Eve 所有权令牌，也不允许两份意识流同时写入或同时发送。

支持的 C2C/群消息先在私有入站日志落盘，网关才提交水位。入站日志本来就支持重启去重；消费
完成但水位保存失败时，恢复补发会读到同一条原件，不制造新的 fresh。
这个处理器只负责日志，不把 fresh 即当作“Eve 已收到/已回了”。手机、通知领取和意识流还需
通过持久序号扫描未完成记录，不能只订阅一次进程内回调后漏掉中断消息。

## 验证与运行边界

`tests/qq_gateway_test.ts` 使用真实回环 HTTP/WebSocket，覆盖 Identify/Resume、慢消费中
心跳、水位不提前、断线排空、积压补发、取消时失败、消费/水位失败、InvalidSession、权限拒绝、
损坏文件保留与同目录第二实例被拒绝。水位和原件实际写文件，不用模型宣称成功替代。

`demo/check-gateway.ts` 是显式的一次真实网关鉴权探针，就绪后停止，或者 20 秒到期停止。
它不发 QQ、不调用模型；若运行期间实际收到消息，入站原文属于真实业务，留在指定私有目录，
不能按临时测试目录清理。输出只有状态与条数，不含 token、用户标识或正文。

这一组件不能证明正式 Eve 上线、自然表达、私信送达、主动消息权限、图像/转发处理、预算、
上下文压缩或自升级。部署仍需接手机/脚本、正式循环、单写者/守护，以及主人身份确认。

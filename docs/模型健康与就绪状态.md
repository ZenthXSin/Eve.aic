# 模型健康与就绪状态

## 排查消息收到后主模型迟迟没有请求

宿主启动时设置 `EVE_TRACE_DIALOGUE_TIMING=1` 可开启只含元数据的阶段计时，默认关闭。`EVE_QQ_TIMING` 记录消息进入通道、任务准入、模型轮次、工具批次和会话保存；`EVE_CONTEXT_TIMING` 记录上下文装配开始/结束；`EVE_HTTP_TIMING` 记录主对话 HTTP 的本地发起、收到响应头及成功解码。记录只有本进程序号、轮次、时间、固定阶段与 HTTP 状态码，不包含消息、路由标识、工具参数、端点或凭据。关闭后不产生这些记录，不增加模型请求或改变超时、重试与回复行为。

- 已收到消息但没有准入：检查同会话的排队、自然消息路由判断或上一代收尾。
- 上下文已开始但未完成：主对话 HTTP 尚未发起；检查语义召回等请求前依赖。语义向量使用独立端点时，该等待不会出现在主模型站点的请求记录中。
- `dispatch` 已出现但没有 `headers`：本地已经发起 HTTP 等待，不代表远端已经确认接收；继续核对网络和供应商处理。站点是否显示在途请求取决于其日志实现，消费账单不能单独证明没有发起请求。
- `headers` 后没有 `decoded`：检查响应体传输、解析或取消；`closed_without_decoded_response` 只表示本地未拿到完整可用响应，不推断远端是否停止。

`request_timing_test.py` 使用实际 Rust QQ 宿主、本地语义与主模型替身，暂停语义查询并断言此时主模型请求数没有增长；解除后验证阶段顺序、完整回复与脱敏。它验证诊断能定位请求前等待，不把合成阻塞当作正式环境的既定原因。

QQ 网关已连接、插件已启动、工具已注册、模型密钥校验通过，这些都不能证明模型能在实际上下文和单次输出上限下完成请求。以前，这些情况在面板上只显示为一个“已就绪”；模型请求因 HTTP 402 失败时，也只能从故障通知里看到状态码。

这份文档把这几件事分开说清楚：

- （#187 第一部分）Provider 失败按固定类别记录，不保存供应商错误正文；
- （#187 第一部分）面板分别显示通道、工具、主模型配置、各用途模型最近的结局与视觉；
- （#187 第一部分）启动时只说明通道已连接、模型尚未验证；
- （#187 第二部分）每个用途可以单独配置单次输出上限，面板显示每个用途实际使用的上限、取自哪个配置键、来源是默认值、环境变量还是覆盖。

## 失败类别

`eve-llm-api` 新增 `ProviderFailure`，包括一个固定类别和可选的 HTTP 状态码，作为 `LlmError::ProviderFailed` 返回。OpenAI 适配器按下表映射：

| 情况 | 类别 |
| --- | --- |
| HTTP 402 | `payment_required`：额度不足，或按当前上下文与单次输出上限不可负担 |
| HTTP 429 | `rate_limited` |
| HTTP 401、403 | `unauthorized` |
| 其他 HTTP 4xx | `rejected` |
| HTTP 5xx | `server_error` |
| 其他非成功状态（如不跟随的重定向） | `unexpected_status` |
| Chat `finish_reason=length`；Responses 未完成且原因为 `max_output_tokens` | `truncated` |
| Chat `finish_reason=content_filter`；Responses 原因为 `content_filter` | `content_filtered` |
| 响应或输出项未完成，原因不明 | `incomplete` |
| 响应自带错误字段，或流中出现失败事件 | `other` |
| 没有收到 HTTP 响应 | `network` |
| 响应超过本地字节上限 | `response_too_large` |

适配器从不读取非成功响应的正文，未知原因也不猜测。超时仍是 `ProviderTimeout`，协议错误仍是 `Protocol`。请求依旧不重试、不跟随重定向、不切换模型。

## 会话失败证据与故障通知

- **会话失败证据**：`SessionFailureEvidence` 新增可选的 `provider_failure`（类别名）。旧记录没有这个字段，按缺省读取；没有类别时不写出。
- **兼容**：含这个字段的状态不能交给旧版本读取，旧版本会因未知字段拒绝启动，原字节保留、不清空，与 #185 新增证据字段的规则一致。
- **QQ 故障通知**：按类别说明原因，例如：
  - “模型服务拒绝请求（HTTP 402），需要检查额度或单次输出预算”；
  - “模型服务限流（HTTP 429）”；
  - “模型回复达到单次输出上限，未完整生成”；
  - “无法连接模型服务”。

  其余规则不变：说明是否已启动工具、本轮已停止、没有自动重试；通知不进入成功交互或训练样本。

## 模型健康记录

- **定义层**：`ModelOutcome`，即一次请求的结局，包括成功、分类的失败、超时、响应不符合协议、配置无法解析；还有 `ModelHealthObserver` 记录入口。
- **实现层**：`eve-model-health`。
  - `ObservedResolver` 包装模型解析器，解析出的 Provider 每次请求结束后记一次结局。它不改变请求和结果，不重试，取消的请求不记录。
  - `HealthBook` 按用途保存以下内容，至多 32 个用途：
    - 请求数、失败数、连续失败数；
    - 最近一次成功的时间；
    - 最近一次失败的类别与时间；
    - 最近一次结局是成功还是失败。
- **组合层**：`eve-qqbot` 为以下用途登记：
  - 对话（`dialogue`）；
  - 开启的后台用途：兴趣观察、研究、实践、技能、工具锻造、主动交流、请求澄清；
  - 计划建议；
  - 偏好提炼（开启记忆学习时）；
  - 反思（开启认知后台时）。

  后台用途的健康记录包在自主运行预算之内：预算拒绝时没有发出请求，不算模型的结局。

**持久化与恢复**：健康记录只在内存中，不写状态存储或文件；进程重启后清零，显示为尚未验证，不补写、不推断重启前的状态。

## 按用途的单次输出上限

所有用途共用主模型（模型名、端点、期限不变），但每个用途可以单独设置单次输出上限。配置在 `runtime.model_uses` 命名空间（Schema 版本 1）：

| 字段 | 环境变量 | 说明 |
| --- | --- | --- |
| `<用途>_max_output_tokens` | `EVE_MODEL_USE_<用途大写>_MAX_OUTPUT_TOKENS` | 0 到 16384；默认 0，表示沿用主模型的上限 |

用途有：`dialogue`、`plan`、`interest`、`research`、`practice`、`skill`、`forge`、`outreach`、`clarify`、`preference`、`reflection`，与健康记录和自主预算的类别同名。

- **优先级**：与其他配置相同，覆盖文件 > 环境变量 > 默认值。可以在面板“插件页面”的 `runtime.model_uses` 页修改。
- **生效时机**：每次模型解析时读取，保存后下一次请求生效，不需要重启。工具执行中的那一轮仍使用本轮开始时的选择。
- **只替换上限**：用途上限非 0 时，只替换该用途请求里的 `max_tokens`（Chat）或 `max_output_tokens`（Responses），不改变模型、端点或期限。
- **不隐式回退**：给出了未知的用途名时，模型解析失败，不改用其他用途或主模型的上限。
- **对话也读取它**：宿主事实里的 `reply_max_output_tokens` 按对话用途的上限给出，模型据此判断是否需要分次完成。

配置服务契约新增 `ConfigService::field_source`，返回字段当前生效值的来源（`override`、`environment`、`default`），不返回值本身。需要重启的字段仍按启动时的值生效，来源也按启动时说明。不提供来源的实现返回 `Unavailable`，面板对应位置留空，不猜测。

**持久化**：用途上限与其他配置一样保存在配置目录的 `config.json`，按配置插件既有的备份与回滚规则恢复；文件损坏时启动失败、原字节保留，不清空。

## 面板与启动

`GET /api/readiness`（需令牌）返回以下内容：

- **通道**：已连接、已关闭、终态错误。
- **对话工具数**：只说明已注册，不代表能成功执行。
- **当前主模型配置**：模型名、协议、单次输出上限，以及上限取自哪个配置键（`provider.openai.max_output_tokens` 或 `runtime.models.primary_max_output_tokens`）和来源。没有上限时注明由服务端决定。
- **各用途的模型状态**：
  - 尚未验证：本进程还没有请求结局；
  - 可响应：最近一次成功；
  - 请求失败：最近一次失败，附类别、状态码与时间；
  - 每个用途还附 `output_limit`，即该用途实际使用的单次输出上限、配置键和来源。没有单独配置时显示主模型的键。
- **视觉**：目前总是“未配置”，图片只接收引用、不解析。

“任务状态”页通道卡片下方新增“运行就绪”区块显示上述内容；读取失败只在本区块提示。未接入健康记录的面板实现返回 503，不显示成已就绪。

启动时，`EVE_QQBOT_READY` 之后多一行 `EVE_READINESS {...}`，内容为：通道已连接、对话工具数、模型尚未验证、视觉未配置。

## 验收

- **Rust 测试**：
  - `eve-llm-api`：类别与状态码；
  - `eve-llm-openai`：402、429 等状态，截断、内容过滤、未完成、网络、超长，以及无重试；
  - `eve-model-health`：结局记录、取消不记录、配置错误、用途上限；
  - `eve-web-panel`：就绪接口需令牌，默认不可用；
  - `eve-config-plugin`：字段来源随覆盖、环境变量变化，需重启字段按启动时说明；
  - `eve-app` 模型解析：对话用途上限只替换请求上限，设为 0 后恢复主模型上限，未知用途解析失败。
- **进程验收** `connectors/qqbot/test/model_health_test.py`：模型先返回 HTTP 402，再返回截断回复，最后正常回复。核对：
  - 故障通知；
  - 失败证据中的状态码与类别，且不含供应商正文；
  - 每次失败恰好请求一次；
  - 面板从“请求失败”恢复为“可响应”；
  - 启动行；
  - 重启后显示为尚未验证；
  - 用环境变量设置对话用途上限后，每次对话请求都按它发送；面板显示它的配置键与“环境变量”来源；宿主事实给出同一上限；去掉后沿用主模型的键。

  可选浏览器验收还核对页面上各用途的上限与来源文字。

## 尚未覆盖

#187 的其余部分另行推进：

- 需显式开启、使用合成内容且不执行工具的代表性上下文就绪检查，它有自己的预算与取消；
- 消息判断的健康登记与用途上限（它使用独立的 Jev 配置与主模型回退）；
- 视觉模型选择见 #186。

面板上的“可响应”只说明最近一次请求成功，不代表用户体验已通过验收。

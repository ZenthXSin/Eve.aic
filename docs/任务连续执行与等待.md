# 任务连续执行与等待

QQ 使用 `--sleep` 注册两个公开 Tool：`sleep` 与 `task_progress`。完整训练启动配置默认包含此开关。

`sleep({"seconds":1})` 等待 1–300 秒后返回实际经过时间。本轮继续请求模型处理剩余任务，不需要用户再发消息。等待是异步、可取消的，单次工具超时为 305 秒。它不持久化、不会在重启后重放；长时间等待、文件变化或进程退出应使用条件唤醒工具，避免循环轮询。

多步任务开始时调用 `task_progress({"status":"in_progress","remaining":"剩余步骤"})`，完成并验证后标记 `completed`；确实缺少权限、必要信息或存在无法解决的阻塞时标记 `blocked`，remaining 写清原因。宿主不会将模型自行标记的完成当成独立验证证据。

本轮仍为 in_progress 而模型返回最终文本时，宿主保留已执行的工具结果，发出续行提示，继续原轮次；最多纠正三次。超限后显式失败，不静默当成完成。普通聊天、未登记的任务、completed/blocked 状态以及工具预算已耗尽的收尾均不触发此机制。模型仍可能遗漏登记，表达约束与机制不能保证所有复杂任务都完成。

状态只存在于本轮共享的 ToolExecutionContext 中，与用户、子代理及后台任务的其他轮次隔离；不产生新用户消息、不重放已执行工具。取消、提供方超时和原有工具预算始终生效。模型流式发出的中间草稿可能已经显示，不能把它当成最终交付。

QQ 过去无开发者配置时默认只允许一批工具；现在默认不限制批次数，仍保留每轮 50 次单独调用的总预算，显式批次参数及开发者配置优先。预算耗尽时工具撤下，只能依据已有证据说明进展和未完成内容。

排查线上历史发现 Provider、ProviderTimeout、Cancelled 等多类失败；部署配置已将批次数设为 0，不能将其所有停顿归因于一批默认值。模型无工具的最终回复原本直接完成轮次，是新显式任务状态需要约束的路径。上游故障仍需单独修复，等待工具不会自动解决故障。

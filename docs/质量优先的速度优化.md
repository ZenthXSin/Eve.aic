# 质量优先的速度优化

先减少本地等待，保留模型、推理强度、输出预算、历史窗口、记忆与工具。优化运行器构建不会自动让上游模型更快；需要分别测量入站到 HTTP 发起、模型请求、模型完成到写出回复三个阶段。

## 运行优化构建

```sh
cargo build -p eve-app --bin eve-qqbot --release --locked
./target/release/eve-qqbot --help
```

同一源码的 `debug/` 未优化构建适合开发。状态快照增长后，每条消息可能触发多次同步序列化与持久提交，未优化运行器的本地开销会变得明显。线上运行应使用 `release/`，参数、插件与原 `--state-dir` 按原配置传入；不能同时启动两个实例占用同一状态目录。切换前等待当前轮次结束并正常停机，保留完整旧状态和二进制。

`prepare_self_upgrade` 继续运行格式、严格 Clippy 和工作区测试，最终二进制使用 `--release` 构建，并从 Cargo metadata 给出的实际输出目录 `release/` 冻结候选。即使存在旧 `debug/` 产物也不会选用。候选校验、切换、故障回退和未知任务不重放沿用原语义；构建优化不取消文件同步或提前宣称写入成功。

## 相同请求对比

以下命令仅连接本地模型与 QQ 替身，不读取真实聊天或凭据，也不向 QQ 发消息：

```sh
python3 connectors/qqbot/test/admission_benchmark.py \
  --binary target/debug/eve-qqbot \
  --binary target/release/eve-qqbot \
  --payload-mib 4 --samples 5 --output /tmp/eve-admission.json
```

每个运行器使用同样的合成状态、消息及立即返回的模型响应。4 MiB 二进制状态值在现有 JSON 字节数组格式下约为 16 MiB 文件。报告包含入站到 HTTP 发起、替身模型、模型完成到回复写出、平台回执持久化的耗时，另核对：模型请求除两次独立实验新产生的情景记忆 `episodes[*].at_ms` 外逐字段一致、`medium` 推理与 8192 输出预算保持、历史完整、工具未移除、合成状态和完成记录可恢复。比较器仅在副本中归零上述合成时间，实际请求仍完整发送；原始严格相等与归一化相等分别报告，正文、ID、修订、模型设置和工具定义均不忽略。这里只衡量本地路径，不把替身模型时延当作真实模型时延；不设置易受 CI 负载影响的绝对时间断言。

使用 `EVE_TRACE_DIALOGUE_TIMING=1` 可在真实实例记录同样的阶段。新增 `reply_written` 表示回复帧已写到 Node，`delivery_confirmed` 表示收到最终平台成功回执并保存；它们均不包含正文、路径、路由 ID 或密钥。前者不等于用户已看到消息，未知投递依然不重发。关闭诊断时不输出这些计时。

端到端耗时仍受模型排队、推理、网络和 QQ 平台影响。在真实模型没有稳定一秒内返回的证据前，不承诺普通聊天一定秒回。

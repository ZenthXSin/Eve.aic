# 生命周期操作与等待取消

`RuntimeLifecycle` 是定义层的宿主生命周期接口，`Kernel` 提供实现。它将启动或停止操作交给宿主管理，并返回可查询的操作 ID。调用方取消一次等待后，已经准入的操作继续执行，结果保留到显式确认。

该接口不通过 `PluginContext` 提供，不赋予插件管理其他插件的权限。组合层可以依赖 `&dyn RuntimeLifecycle`，而无需依赖 Kernel 内部结构。

## 提交、等待与确认

| 接口 | 行为 |
| --- | --- |
| `submit(request)` | 等待串行准入，登记操作并返回 `LifecycleOperationId` |
| `operations()` | 返回按 ID 排序的独立快照，读取不移除结果 |
| `wait(id)` | 等待终态，可重复调用；取消等待不取消操作 |
| `acknowledge(id)` | 移除终态报告；运行中返回错误，未知 ID 返回 `false` |

请求包括 `LifecycleRequest::Start(id)`、`StartAll`、`Stop(id)` 和 `StopAll`。ID 只在所属 Runtime 中有效，不能跨 Runtime 使用。

默认 Kernel 实现需要正在运行的 Tokio 执行器才能提交；缺少执行器时返回错误，不开始修改插件。抽象接口本身不要求其他实现使用 Tokio。

生命周期 worker 使用提交首次轮询时所在的 Tokio 执行器。多个执行器共享一个 Kernel 时，关闭承载已开始操作的执行器也会触发整个 Kernel 的中断隔离；宿主应统一管理执行器的退出顺序。

对应的 Kernel 方法是 `submit_lifecycle`、`lifecycle_operations`、`wait_lifecycle`、`acknowledge_lifecycle`。以下宿主代码通过抽象接口提交并保留结果：

```rust
use eve_plugin_api::{
    LifecycleOperationState, LifecycleRequest, PluginError, PluginId,
    PluginResult, RuntimeLifecycle,
};

async fn start_plugin(
    runtime: &dyn RuntimeLifecycle,
    plugin: PluginId,
) -> PluginResult<()> {
    let id = runtime.submit(LifecycleRequest::Start(plugin)).await?;
    let operation = runtime.wait(id).await?;
    let result = match operation.state {
        LifecycleOperationState::Completed(result) => result,
        LifecycleOperationState::Interrupted(error) => Err(error),
        LifecycleOperationState::Running => {
            return Err(PluginError::Lifecycle("等待返回非终态".into()));
        }
    };
    // 先保存或报告实际结果，再确认释放记录；此处示例直接输出。
    println!("操作 {id} 的结果：{result:?}");
    runtime.acknowledge(id)?;
    result
}
```

`wait` 返回值有两层含义：外层 `Err` 表示无法取得报告，例如 ID 不存在；外层 `Ok` 表示取得了终态报告，操作是否成功由 `state` 决定。不能把 `wait(id).await?` 视为启动或停止已经成功。

| 操作状态 | 含义 |
| --- | --- |
| `Running` | 已准入，等待执行或正在执行，尚无终态 |
| `Completed(Ok(()))` | 操作成功返回 |
| `Completed(Err(error))` | 操作及其错误收尾已返回，但仍可能有未退出任务、清理失败等问题 |
| `Interrupted(error)` | 执行器关闭等原因中断操作，不能视为已经完成异步清理 |

操作状态和插件状态是两个维度。例如停止得到 `Completed(Err(...))` 时，插件可能因为 Cleanup 失败而为 `Stopped`，也可能因任务未退出而为 `Failed`。应结合 [运行时诊断](./运行时诊断.md) 检查实际状态与错误。

## 取消等待的边界

尚未轮询的提交 Future 不产生副作用。等待串行准入锁时取消提交，也不会启动或停止插件。准入后操作由宿主独立持有，返回 ID 前已经登记；此时丢弃或超时取消 `wait` 只影响本次等待，不移除报告，也不撤销操作。

默认实现中，已准入的后台执行任务持有 Kernel 的强引用。因此，调用方丢弃自己的 Kernel 变量也不会中止该操作；只要执行器继续运行，后台任务就会持有 Runtime，直到操作返回。这种所有权不能保证执行器关闭后继续收尾。

取消等待不是停止协议。若业务希望在启动完成后再停止插件，应继续查询该操作，并显式提交 `Stop` 或 `StopAll`；新请求依次准入，不与当前生命周期操作并发执行。

兼容入口 `Kernel::start`、`start_all`、`stop`、`stop_all` 仍可直接等待：它们提交操作、等待实际结果，在正常返回时自动确认报告，包括返回业务错误的情况。包装器独立持有本次记录，即使其他宿主先确认，也仍能返回自己的真实结果。若调用方在准入后丢弃包装器的等待，操作仍继续，报告会保留；宿主可通过 `operations()` 查到它。需要从一开始保留明确操作 ID 时，应使用显式提交接口。

`tokio::time::timeout` 包裹等待不会为操作设置执行期限。插件启动、Cleanup 和自定义后端必须能够推进，不能同步阻塞执行器或无限等待；否则当前操作会持续占用生命周期准入，后续请求无法执行。

## 报告容量与所有权

`KernelConfig::lifecycle_report_capacity` 默认是 `128`。运行记录和未确认的终态报告都占容量；容量满时拒绝新请求并返回错误，不静默丢弃旧结果。设为 `0` 会拒绝全部提交。宿主应定期查询操作，将重要结果保存到自己的日志或存储后调用 `acknowledge`。

同一个 ID 可以有多个等待者。已经开始并取得记录的 `wait` 独立持有该记录的引用，即使另一个宿主确认并移除可发现的报告，它仍能返回原终态。确认之后新开始的 `wait` 才会报告 ID 不存在；仅构造但还未轮询的等待 Future 不保证已取得记录。

确认会从全局操作清单移除报告，而非取消已有等待者。多个宿主组件共享接口时，应明确由谁记录结果并确认，避免过早释放尚未开始等待的调用方仍需查询的报告。

这些记录仅存在于当前 Runtime 的内存中，**不提供跨进程恢复**。进程重启后需要重新注册、启动插件；字节状态持久化仍由 `StateStore` 后端负责。操作失败、等待取消或报告确认都不会自动撤销已经成功写入的状态，详见 [状态持久化](./状态持久化.md)。

## 执行器关闭与中断

宿主必须保持 Tokio 执行器运行，直到需要完成的生命周期操作真正返回。取消调用方的等待与执行器丢弃实际操作是不同情形；后者按操作是否已经开始执行区分处理：

| 中断时机 | 报告与后续行为 |
| --- | --- |
| 操作已登记，但后台执行任务尚未首次轮询 | 报告为 `Interrupted`，插件未被该操作修改，Kernel 不被隔离；可在运行中的执行器上重新提交 |
| 操作已经开始，执行器关闭等原因使它意外中断 | 报告为 `Interrupted`，整个 Kernel 被隔离，拒绝新的生命周期操作，并关闭全部插件 Context |

开始前中断的报告也占用容量，需要按普通终态报告确认。重试创建新操作，不会继续执行旧报告对应的后台任务。

开始后中断时，原为 `WaitingDependencies`、`Starting`、`Active` 或 `Stopping` 的插件都转为 `Failed`，包括当前操作之外已经运行的插件。这表示整个 Runtime 已无法安全继续，不表示每个插件的代码都发生了错误。`Registered`、`Stopped` 或原有 `Failed` 状态不会因此改成其他状态。

关闭 Scope 可以拒绝旧 Context 后续使用，但无法代替异步任务停止和 Cleanup。中断时不承诺异步清理完成，已经登记而未执行的 Cleanup 及其捕获资源可能继续保留在旧 Scope 中，直到宿主丢弃旧 Kernel、Context 及其他持有引用。这避免在 panic 的 Drop guard 中执行用户析构；并不保证全部句柄立即释放，确认操作报告也不会补做这些清理。

宿主应记录中断原因、检查外部资源，并在已开始的操作被中断后使用新的 Runtime 重新装配。原有字节状态继续按持久化后端的语义保留，不能把 `Interrupted` 解释为停止成功。

正常退出应主动提交停止并等待终态，再确认结果和刷新日志，最后关闭执行器。Rust panic 隔离范围仍以 [插件开发](./插件开发.md#启动与清理的-panic-边界) 中的说明为准。

## 实际验收示例

```powershell
cargo run -p eve-runtime --example lifecycle_operations --locked
```

示例插件通过 `Notify` 暂停 Cleanup。宿主使用 `&dyn RuntimeLifecycle` 提交启动并确认，再提交停止：第一次 `wait` 超时后，操作记录仍为 `Running`；放行 Cleanup 后，重新等待取得真实成功结果，并核验清理已经执行。读取和重复等待都保留终态，最终通过 `acknowledge` 释放报告。

示例成功时输出类似：

```text
启动操作 1 已完成并确认。
停止操作 2 的一次等待已超时；超时后记录仍为 Running。
再次等待取得实际终态：Completed(Ok)，Cleanup 已执行，报告仍可查询。
已确认并移除停止报告；操作记录数为 0，日志已刷新。
```

操作 ID 以实际运行为准。示例中的短超时用于演示取消等待，不是生产环境的生命周期执行期限。

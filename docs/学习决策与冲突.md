# 学习决策与冲突

自主偏好学习在候选进入 Memory 前保存一条可查询的决策，区分新建、更新、暂缓和拒绝。用户可以核对系统为什么采纳候选、采用了哪批交互证据，以及是否真的写入了记忆。开启方式沿用 `--self-learning`，普通 `--memory --memory-learning` 仍由用户明确确认；提炼、Context 和分段发送的基础规则见[自主偏好学习](./自主偏好学习.md)。

## 决策与记忆状态

定义层 `eve-learning-api` 的 `LearningDecisionAction` 有四种动作：

| 动作 | 含义 | 后续处理 |
| --- | --- | --- |
| `Confirm` | 候选满足准入条件，可以建立新偏好 | 宿主复核后尝试一次 Memory CAS |
| `Update { preference_id, expected_revision }` | 候选可以更新一个明确的已有偏好版本 | 宿主复核目标、来源和版本后尝试一次 Memory CAS，保留旧版历史 |
| `Defer` | 当前证据门槛未满足、冲突不明确或策略暂不允许 | 保留候选及理由，本次不写 Memory |
| `Reject` | 当前规则判定不应自动采纳，例如已有等价记录或撤销屏障 | 保留候选及理由，本次不写 Memory |

决策只说明该次判断。`Confirm`、`Update` 不是成功回执；只有 Memory 中可与候选、来源及目标版本核对的偏好历史，才能证明新建或更新已保存。CAS 冲突、容量不足以及提交确认丢失，都可能使决策记录与实际记忆状态不同。查询不能仅凭动作显示“已保存”。

每条 `LearningDecisionRecord` 保存范围内连续序号、时间及 `LearningDecision`。决策包含候选 ID、批次 ID、策略版本、读取时的 Memory 修订、原始证据 ID 列表、动作和原因；更新动作另保存目标偏好 ID 和期望版本。记录不复制候选正文，也不把模型自评改称事实概率。

## 来源与更新边界

内置 `EvidenceConfirmationPolicy` 的版本为 `evidence-conflict-v2`，是无模型调用的纯判断策略。候选与批次须绑定同一个可信 `MemoryScope`，引用本批实际完成交互，且完整证据仍与当前 Memory 一致。QQ 范围沿用 AppID、私聊或群、目标及发送者绑定，用户正文、候选 ID 和证据 ID 不能扩大范围。

内置策略要求候选未过期、模型自评至少 80、至少两条真实完成交互引用。自评及引用数量只能决定准入，不能证明模型正确理解了长期偏好；助手自述、用户沉默或模型解释不构成新的用户授权。可信宿主替换策略时可以选择不同的自评和引用数量门槛，来源、期限与冲突边界仍由宿主复核，见下文[替换策略](#替换策略)。

自动更新仅处理规则能够完整识别的单项节奏偏好：是否分段、最多段数、段间停顿。它要求只找到一个同类目标，目标仍然有效，全部版本的来源均为可核对的 `CompletedInteraction`，新候选的最新来源修订严格晚于目标当前版本的来源修订。Memory 没有独立的“自动”标记，这里依据每版来源类型判断；不要求偏好 ID 带 `learned-` 前缀。这里比较来源修订，不依赖主机时间先后。

例如，已有自动保存的“回复最多2段”，之后新的完成交互形成“回复最多3段”候选；满足证据和唯一目标约束时，可以更新原偏好并保留两段的历史。若用户通过 `/correct-memory` 修正过该偏好，或通过 `/forget` 撤销过它，后台不能覆盖这个决定。已有相关历史时，非严格单项的候选不能更新；存在多个可能目标或新来源并不更新时，也保留候选并给出暂缓或拒绝原因。系统不保证识别任意自然语言混合句。

当前有效正文与候选有限规范化等价时，不重复新建；撤销记录的任一历史版本等价时，不自动恢复。有手动来源的历史正文等价时，也保留手动决定。全部来源均为完成交互、当前仍有效的偏好，其旧历史正文不会单凭文本重现就阻止更新：明确单项节奏在来源更新等条件满足时仍可改回旧值。规范化只去除首尾空白、将连续空白合并成单个空格，并去掉末尾句号 `。` 或 `.`；不去掉正文内的全部空格，不折叠大小写。严格节奏规则中同字段、同数值的句式也视为等价。确需重新建立已撤销偏好时，用户仍可发送明确 `/remember` 命令。

允许更新的严格节奏规则接受完整单句，可有一个“请”前缀，数字两侧可以有空白。例如“回复最多2段”“回复最多分成三段”“每条回复最多两段”；段数仅为 2–5。停顿可用 0–200 的百分比及 `％`，或“段间不要停顿”“段间停顿短一点”“段间停顿长一点”等明确句式；这些比例沿用分段器的节奏含义，不是固定毫秒数。多项混合句和未列入严格规则的措辞不会因此获得更新权限。

较宽的检查另外按逗号、分号、句号或换行扫描已知节奏子句，可忽略子句内空白和末尾 `!`、`！`，并识别数字前的 `+` 及 6–8 段。这些是发送端可识别、而严格更新规则不授权的形式，例如“回 复 最 多 3 段！”、“回复最多+3段”、“回复最多6段”。该检查不把任意文本判成等价，也永不授予 `Update`。

完整候选最多包含 8 个非空子句，每个子句均能识别、同字段数值一致，且所有涉及字段在任何偏好历史中都没有相关记录时，保留首次 `Confirm` 能力。例如尚无相关历史时，“回复最多分成两段，段间不要停顿”可以按同一条偏好首次保存，仍须通过证据及期限等检查。出现相关历史时，撤销或手动来源屏障优先；即使相关历史全部来自完成交互，也暂缓而不更新。同字段值矛盾、已知节奏子句混合未知子句或超过 8 个子句时，同样暂缓。纯自由文本没有任何已知节奏子句时沿用原准入行为，不据此猜测语义冲突。

有限规范化及明确句式规则不进行语义检索，不声称识别任意近义句或解决所有偏好矛盾；称呼、解释风格等自由文本继续依赖来源约束、候选查看及用户纠正。

## QQ 查询

| 命令 | 行为 |
| --- | --- |
| `/memory-candidates [页码]` | 查看当前会话候选、实际关联状态和决策摘要 |
| `/memory-decision 候选ID` | 查看当前会话该候选最近 8 条决策及历史总数，另与 Memory 核对实际保存状态 |
| `/memories` | 核对当前偏好及历史状态 |
| `/accept-memory 候选ID` | 手动确认尚可确认的候选，沿用明确命令来源 |
| `/correct-memory 偏好ID 内容`、`/forget 偏好ID` | 明确纠正或撤销已有偏好，后台保留这些决定 |

详情列出决策序号、时间、策略版本、读取时的 Memory 修订、来源证据 ID、动作、理由；更新记录另列出目标 ID 和期望偏好修订。实际保存部分显示能核对的偏好 ID、当前版本及状态，或者说明尚无对应保存；不能把旧决策中的 Memory 修订当成当前值。

查询只读本地持久状态，零模型调用；不会因为查看候选补发提炼、重放确认或扩大访问范围。未记录自动决策不等于拒绝，也不等于用户没有偏好。关闭自主模式后保留既有决策与记忆，是否装配已确认偏好仍由 `--memory` 决定。

## 保存、冲突与恢复

原候选文档 `eve.learning` 命名空间中的 `learning.v1` 保持格式 1；新增独立状态键 `learning.decisions.v1`，格式同为 1。决策文档全局最多 1024 条、4 MiB，与原 Learning 文档的 128 批、4 MiB 分别计量；不自动淘汰历史或清空满容量文档。

决策按单个范围从 1 连续编号，由 Learning 实例的同一互斥锁串行追加。保存时再次核对该范围已完成批次中的不可变候选、批次与证据引用，记录中的 Memory 修订不能早于批次读取的记忆修订。对同一候选重复得到最近一次相同判断时，复用原记录、时间和读取修订，不新增记录也不写存储；仅 Memory 修订变化不会使相同判断产生新历史。动作、理由、目标版本或策略版本等变化时，可以追加新的决策。

宿主先保存自动决策，再执行 Memory CAS。两个文档没有跨插件事务，决策不负责证明 Memory 已提交。进程可能在决策落盘后、Memory 调用前退出，也可能在 Memory 已提交但确认尚未返回时退出。重新打开后必须读取真实持久状态，核对来源、当前记忆及目标历史；不能只凭旧决策重复写入，也不能因为未收到确认就宣称操作失败。

Memory CAS 冲突后重新扫描和复核，不覆盖并发用户命令；目标已经修正或撤销时应遵守当前状态。达到决策或记忆容量上限时保留原候选和全部历史，不把未提交动作标为成功。存储写入错误可能已经提交，当前实例关闭读写，宿主停止并保留现场；重启核对实际字节，不继续使用旧缓存覆盖后端。

恢复先严格校验候选和决策两份文档，再允许将旧 `Running` 批次写为 `Interrupted`。未知版本、重复键、无效序号、候选或来源关联不符等错误阻止继续使用；不清空数据或退回空状态。旧目录缺少 `learning.decisions.v1` 时将其视为空历史，不做迁移、不补写空文档。旧批次自身有 `Running` 时，仍按既有规则保存中断状态；这不表示新决策格式导致历史迁移。无待处理变化的再次启动不改写两份文档。

文件与 PostgreSQL 都经公开 `StateStore` 保存，沿用宿主选定的后端及提交失败规则；升级不会自动搬迁已有文件历史。

## 替换策略

`AutoConfirmationPolicy` 保留原 `allows` 接口，同时提供带版本的 `decide` 判断。既有实现默认使用 `legacy-auto-confirm-v1`，将允许映射为 `Confirm / Eligible`，不允许映射为 `Defer / PolicyDenied`。可信宿主可继续通过 `run_qqbot_with_learning_policy` 替换策略；关闭自主模式时不调用策略。

自定义策略只返回判断，不持有记忆写能力。宿主仍核对范围、期限、完整来源、重复与撤销屏障，以及更新目标和版本；策略返回 `Confirm` 或 `Update` 不会绕过这些边界。`LearningAdmin` 新增 `decisions(scope)` 和 `record_decision(scope, decision, at_ms)`；旧实现保留源码兼容，但默认返回 `Unavailable`。新 QQ 宿主查询候选或处理确认命令时也必须能够读取决策账本，不能将不可用误当作空历史；替换持久实现须显式提供这些能力，自动流程另须支持保存决策。

80 分、两条引用是内置策略门槛，宿主的 `constrain_decision` 不把它强加给替换策略。例如自定义策略可允许自评 73、引用一条真实完成交互的候选；该引用仍须属于确切批次和当前可信范围，并通过完整来源、期限、重复、手动与撤销历史复核。更新还须满足唯一目标、期望版本、全部历史完成来源以及新来源修订要求。宿主只收窄策略提议，不将 `Confirm` 自动升级为 `Update`，也不将 `Defer` 或 `Reject` 改成允许。

这一步让有限规则下的偏好更新具备可查看的理由和恢复依据；不修改模型权重，不提供任意语义冲突合并或完整 AGI 能力。

## 本地验证入口

决策 API、规则策略和账本测试分别覆盖公开契约、有限冲突规则、严格恢复和写入失败；规则用例位于 `crates/learning-plugin/tests/decision.rs`。QQ 命令测试核对作用域、只读查询及真实保存状态。实际 Eve 进程测试位于 `connectors/qqbot/test/learning_decision_test.py`，使用本地模型与 QQ 桥接替身核对提炼后的决策、Memory 更新、用户纠正屏障和重启行为：

```sh
cargo test -p eve-learning-api -p eve-learning-plugin --locked
cargo test -p eve-app qq_learning_commands --locked
cargo build -p eve-app --bin eve-qqbot --locked
EVE_QQBOT_BINARY=target/debug/eve-qqbot python3 connectors/qqbot/test/learning_decision_test.py
```

`scripts/fixtures/learning-decision-rules.json` 保存人工定向规则案例，可用 `cargo test -p eve-learning-plugin --test decision curated_rule_regressions -- --nocapture` 查看旧布尔准入与新四态判断的逐项差异。它是已声明规则的回归集，不是独立留出语义评测，不能据此推断泛化能力或 AGI 进展。

这些命令用于本地复验；进程测试中的模型和桥接替身不能证明真实模型候选质量或 QQ 实机送达，实机体验另行测试。

# 运行时诊断与停止错误

`RuntimeInspector` 是定义层的宿主只读诊断接口，`Kernel` 提供默认实现。监控、命令行和测试可以依赖这个接口查询插件及任务，无需访问 Kernel 的私有注册表。

该接口面向组合层和宿主，不通过 `PluginContext` 授予插件查询其他插件或管理 Runtime 的能力。插件仍通过自己的 Context 查询自身任务；诊断接口也不包含启动、停止或重启方法。

## 查询插件与任务

```rust
use eve_plugin_api::{PluginResult, RuntimeInspector};

fn inspect(runtime: &dyn RuntimeInspector) -> PluginResult<()> {
    for plugin in runtime.plugins()? {
        println!(
            "插件 {}，版本 {}，状态 {:?}",
            plugin.info.id, plugin.info.version, plugin.state
        );
        for task in runtime.plugin_tasks(&plugin.info.id)? {
            println!(
                "任务 {}，类型 {}，状态 {:?}，成功次数 {}，已退出 {}",
                task.id, task.task_type, task.state, task.runs, task.exited
            );
        }
    }
    Ok(())
}
```

`plugins()` 返回按插件 ID 排序的 `Vec<PluginStatus>`，每项包含 `PluginInfo` 和 `PluginState`。可见状态包括 `Registered`、`WaitingDependencies`、`Starting`、`Active`、`Stopping`、`Stopped`、`Failed`。

查询不等待异步生命周期锁，因此插件启动 Future 或停止清理仍在等待时，宿主可以观察 `Starting`、`Stopping` 等中间状态。查询仍需短暂读取各自的数据锁，不承诺完全无阻塞。

这些数据是**逐项快照**，不构成同一时刻的全局事务快照。读取下一个插件或继续查询任务时，生命周期可能已经发生变化；宿主应允许相邻两次查询看到不同结果。

`plugin_tasks(id)` 返回该插件的任务信息，也保留停止后尚未确认退出的任务。已注册插件没有任务时返回空列表；未注册插件返回错误，不能用空列表掩盖无效 ID。后端查询失败也向上传递错误。

## 停止错误的结构

`stop` 和 `stop_all` 在多个插件或阶段出现错误时继续执行可执行的收尾步骤，并通过 `PluginError::Shutdown(Vec<PluginStopError>)` 返回诊断。每项保留实际出错插件、停止阶段和底层 `PluginError`，同一个插件可以有多项错误。

这里保留的是阶段错误。Scope 内多个 Cleanup 回调的错误仍合并为 `PluginError::Cleanup` 字符串，并未保留每个回调各自的错误枚举。

| 阶段 | 含义 |
| --- | --- |
| `StopStage::Tasks` | 任务管理器停止失败，或报告任务超时、执行错误等问题 |
| `StopStage::Cleanup` | Scope 中的资源清理动作返回错误，或其工厂调用、Future 轮询发生 unwind panic |
| `StopStage::Inspection` | 收尾后仍有未退出任务，或无法查询任务以确认退出 |
| `StopStage::Lifecycle` | 其他停止流程错误 |

停止提供者时会先停止依赖它的消费者。消费者的错误继续归属于消费者，不会被重新标成提供者的错误。宿主可以直接匹配结构，无需解析错误字符串：

```rust
use eve_plugin_api::{PluginError, StopStage};

fn report(error: &PluginError) {
    match error {
        PluginError::Shutdown(failures) => {
            for failure in failures {
                let stage = match failure.stage {
                    StopStage::Tasks => "任务停止",
                    StopStage::Cleanup => "资源清理",
                    StopStage::Inspection => "退出确认",
                    StopStage::Lifecycle => "生命周期",
                };
                eprintln!(
                    "插件 {}，阶段 {}：{}",
                    failure.plugin, stage, failure.error
                );
            }
        }
        PluginError::Rollback { cause, errors } => {
            eprintln!("原始启动错误：{cause}");
            for error in errors {
                report(error);
            }
        }
        error => eprintln!("运行时错误：{error}"),
    }
}
```

启动失败引发已启动依赖回滚时，若回滚也失败，`Rollback` 同时保留原始 `cause` 和回滚 `errors`。宿主应记录两者，避免清理错误覆盖启动失败原因。

## 生命周期 panic 的诊断

`Plugin::start` 的同步调用或所返回 Future 的轮询发生 unwind panic 时，Kernel 将其转换为启动错误，执行任务停止、Scope 清理和本次依赖回滚。出错插件最终为 `Failed`；若回滚还发生错误，原始启动原因与回滚错误继续按上述 `Rollback` 结构保留。

正常停止期间，Cleanup 工厂或其 Future 轮询的 unwind panic 进入 `Cleanup` 阶段错误。Scope 继续逆序执行其余回调，Kernel 继续收尾其他插件，保留真正出错插件的归属。一个回调的 panic 不能用来推断其余回调也没有执行；应检查完整阶段错误及最终状态。

捕获 panic 不会关闭 Rust panic hook，标准错误仍可能出现 panic 输出。判断是否完成收尾应依据返回值和状态查询，不能只依据标准错误是否有 panic 字样。

这些诊断以生命周期操作完整返回为前提；`panic=abort`、双重 panic、析构 panic，以及宿主取消生命周期 Future 均不在恢复保证内。自定义后端仍须以 `Err` 报告可处理错误。详细边界见[插件开发](./插件开发.md#启动与清理的-panic-边界)。

## 停止结果与生命周期状态

是否返回错误和最终生命周期状态表达不同信息，需要一起查看：

- 已确认所有任务退出时，插件进入 `Stopped`。即使某个 Cleanup 动作返回错误或发生被捕获的 panic，或任务先超时再被确认退出，停止调用仍报告对应错误。
- 仍有任务未退出时，插件进入 `Failed`，保留残余任务用于诊断。
- 无法查询任务确认退出时，也进入 `Failed`，报告 `Inspection` 错误，不能假定停止成功。
- `Failed` 插件禁止自动重启，避免旧任务与新实例同时操作外部资源。它与启动失败形成的 `Failed` 一样，需要宿主处理。

`Stopped` 说明生命周期停止及任务退出已完成，并不代表所有外部清理动作都成功。宿主不能只看状态而忽略停止调用返回的错误。

Cleanup 是一次性动作。重复调用 `stop` 不会重新执行已经失败的清理动作；已进入 `Failed` 的插件也不会通过重复停止自动重新收尾或转为 `Stopped`。宿主应在第一次收尾时记录完整错误，并根据业务情况处理残余资源。

## 实际验收

```powershell
cargo run -p eve-runtime
```

示例通过 `&dyn RuntimeInspector` 查询四个插件，检查消费者、提供者和任务示例均为 `Stopped`，预期启动失败插件为 `Failed`，四者均无残留任务。成功后输出：

```text
诊断验收通过：已通过抽象接口检查 4 个插件的最终状态，停止与回滚后均无残留任务。
```

Runtime 集成验收同时断言诊断插件数量；具体阶段错误与生命周期边界由 Kernel 测试覆盖。

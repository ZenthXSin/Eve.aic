# 请求澄清

这是[认知能力路线](./认知能力路线.md)第 4 项"长期目标与资源分配"中"请求澄清"的第一部分。

以前，兴趣学习目标在当前版本卡住之后，什么都不会发生。例如实践尝试用尽仍未验证，或者运行环境做不了这件事：每个目标版本只研究、只实践一次，所以后台不会空转，但用户也不知道 Eve 卡在了哪里。请求澄清让 Eve 在这种时候问用户一个具体问题。用户补充的信息作为普通聊天进入记忆，由[兴趣观察](./兴趣观察.md)照常处理：兴趣有了新的原话，学习目标就有了新版本，研究与实践随之重新开始。

## 启用

```bash
./target/debug/eve-qqbot --state-dir .eve-qqbot --interest-learning \
  --practice-mindustry-server /opt/mindustry/server-release.jar --clarify
```

- `--clarify` 默认关闭。它需要同时开启受控研究（`--research-source`）或实践运行环境，作为判断目标是否卡住的依据，可以和 `--outreach` 同时开启。
- 撰写问题与判断时机复用主模型配置与 `EVE_OPENAI_API_KEY`。
- 开启[自主运行预算](./自主运行预算.md)时，这两类请求按 `clarify` 用途记账：余额不够时不撰写新问题，本条消息也不判断时机。

QQ 命令：
- `/clarify`：查看 Eve 因为卡住而问过自己的问题，包括卡住的原因、状态、问题原文和用户的回复。
- `/clarify off`：请 Eve 不再附带这类问题。
- `/clarify on`：恢复。

问题只属于来源用户，其他用户看不到。未开启时回复"请求澄清未启用。"。

## 什么算卡住

宿主只按账本中已经结束的记录做确定性判定，不调用模型。范围是等待中、由兴趣派生的学习目标，只看目标的当前版本：

| 卡住原因 | 判定依据 |
| --- | --- |
| 实践尝试用尽仍未验证 | 开启实践时，该版本的实践记录为 `Unverified` |
| 现有运行环境做不了 | 开启实践时，该版本的实践记录为 `NotApplicable` |
| 研究没有找到资料 | 只开启研究时，该版本的研究已完成，但没有附逐字引用的知识 |

开启实践时只看实践。研究没找到资料时实践仍会尝试，所以先等实践的结局。模型请求失败、超时、中断都不算卡住：这些是基础设施问题，不是需要用户补充的信息。兴趣已撤回或没有可引用的原话时，不提问。

## 流程

1. **准入**：每个目标版本至多问一次。问题 ID 由目标与版本确定性生成。先保存 `Composing`，才发起撰写请求。
2. **撰写**：一次无工具模型请求。输入只含宿主整理的事实：用户原话、Eve 实际做过的尝试与结果（例如"实际做了 3 次最小产物，在运行环境中都没有验证通过；最后一次的问题：……"），以及运行环境能做的产物。输出必须是严格 JSON，问题至多 1024 字节并且包含问号。失败、超时、取消都记为失败，不重试。
3. **时机**：用户下次私聊找 Eve 时，复用主动交流的时机判断器，先保存判断，再看用户这条消息与 Eve 的回复。同一条消息只判断一次，每个问题至多判断 12 次；用完仍没有合适的时机就不再等待。
4. **附带**：判断为合适后，先保存投递尝试，再把问题作为最后一段随这条私聊的被动回复发出，以平台回执为准。没有写出或平台拒绝时回到等待，至多尝试 6 次。只附带在私聊回复中，不主动私聊，群聊、命令确认与控制消息不附带。同一用户默认 24 小时内至多送达一个问题。
5. **回复**：送达后 3 天内，用户的下一轮私聊（不是附带问题的那条）记为回复，保存消息 ID、记忆证据 ID 与用户原话的前 512 字节。过了 3 天仍没有私聊，记为过期。这里只记录"下一轮"，不判断它是否真在回答问题；语义由兴趣观察处理。
6. **取消**：送达前，目标有了新版本（例如用户自己补充了信息），问题就过时了；目标结束或兴趣被撤回，也没必要再问。这两种情况都会取消问题。

与[主动交流](./主动交流与邀请.md)同时开启时，两者共用通道的投递点：邀请优先判断；投递结果按 ID 前缀（`invite-`、`clarify-`）交回各自的账本，找不到对应来源时报错，不静默丢弃。

## 持久化与恢复

账本是 `eve.clarify` 插件的 `clarify.v1`：问题记录（准入、事实、撰写、每次判断、每次投递尝试、回复）与用户偏好。

- **每一步先保存再执行**：外部动作之前，对应的状态已经保存。
- **重启**：
  - 撰写中的问题记为中断，不重放；
  - 判断中的消息记为中断，不再判断这条消息；
  - 发送中的投递记为结果未知，不重发，也不当作已送达。
- **严格读取**：读取时拒绝以下情况：
  - 重复键、未知字段、版本不符；
  - ID 与目标版本不一致；
  - 问题没有问号；
  - 回复来自附带问题的那条消息；
  - 状态与记录不一致，例如已送达却没有成功回执；
  - 重复的问题或偏好。
- **损坏时拒绝启动**：遇到上述问题时宿主拒绝启动，原字节保留，不清空。
- **写入失败**：提交可能已经完成，也可能没有。此时实例关闭，后台随之停止，宿主停止准入；重新启动后按账本核对。
- **容量**：至多保存 128 个问题、256 个用户偏好，满了保留原记录，不再新增问题。

## 分层

- **定义层**：`eve-clarify-api` 规定卡住原因、事实、问题记录、投递策略，以及 `ClarificationComposer` 与 `ClarifyAdmin` 契约。
- **实现层**：`eve-clarify-plugin` 提供持久账本与模型撰写器。
- **组合层**：QQ 宿主负责卡住判定、后台撰写与回复记录、通道投递适配与 `/clarify` 命令。时机判断复用主动交流的公开 `TimingJudge` 契约。

撰写器、判断器和账本都可以替换。

## 尚未覆盖

- 后续创作目标与用户自己的待办还不会提问。
- 回复不经模型判断，只记录"下一轮私聊"。
- 不主动私聊；是否值得主动私聊需要正式 QQ 环境的体验验收。
- 提问质量只经确定性替身验证，真实模型的效果另行评估。

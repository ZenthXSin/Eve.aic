# 运行守护与故障兜底

实时升级监督器现同时处理启动失败和运行中退出；Linux 可再套一层外部守护。只在旧实例及其受管桥接进程全部退出后启动替代实例。两层恢复各有独立预算，默认每十分钟至多恢复三次，间隔一、二、四秒；次数写入磁盘，重启监督器不会清空记录。

## 内层：程序退出与升级回退

`self_upgrade_runtime.py` 保存上一版命令、二进制和运行资源摘要。候选通过就绪与短期健康观察并提交后，如果随后崩溃，监督器重新核对上一版二进制与资源，回退程序，并隔离失败候选。仅资源发生变化的升级也适用。同一候选再次申请会被拒绝；修复后应生成新的候选。

没有可用上一版时，验证当前程序和资源后限次重启。Linux 程序拥有独立进程组，崩溃残留的桥接先退出，再启动替代程序。新进程必须再次通过就绪与健康检查；恢复启动失败不会无限重试。此策略针对进程退出，不把长任务或网络暂时断开认作崩溃。

`supervisor.json` 保持原有八字段协议；`recovery.json` 单独保存退出历史与恢复结果，`previous-command.json` 保存上一版验证信息，`quarantine/` 保存失败候选标记。主状态中的 `result` 可见 `runtime_restarted_state_preserved` 或 `runtime_rolled_back_binary_state_preserved`。

## 外层：监督器退出

Linux 使用 Python 3.11 或更高版本，例如：

```sh
python3 scripts/service_guard.py --directory /srv/eve/guard -- \
  python3 scripts/self_upgrade_runtime.py \
  --directory /srv/eve/control --candidates /srv/eve/candidates -- \
  /srv/eve/eve-qqbot --state-dir /srv/eve/state --agent /srv/eve/AGENT.md \
  --bridge-script /srv/eve/connectors/qqbot/bridge.mjs
```

实际运行仍需完整业务参数和环境变量；上例仅展示两层嵌套关系。守护与监督器脚本必须位于同一目录。

外层为监督器建立独立 Linux 会话，记录启动身份与存活成员。监督器被异常终止时，先关闭这次会话中仍存活的受管进程组，再按预算启动监督器。使用文件锁防止重复守护。发现旧监督器或不明残留会话仍活跃时停止，不凭旧 PID 杀进程，也不收养来源不明的实例。自行脱离会话的后台进程不在自动清理范围。

查看 `guard/guard.json` 的阶段、心跳、监督器 PID 和退出原因；`guard/guard-recovery.json` 保存外层恢复次数。`running` 仅表示监督器进程存活，QQ 连通和模型状态仍以运行器就绪接口为准。

正常停止应向**外层守护 PID**发送 SIGTERM，并等待其退出；它会要求监督器正常关闭程序。监督器主动正常退出或返回明确的保护性退出码 78 时，守护也停止，不重新拉起。

## 状态和边界

- 仅回退程序和资源，始终使用同一份最新状态。备份只供人工核查，不自动覆盖状态目录。
- 不重放中断的升级请求、工具任务、历史消息或投递结果未知的回执。恢复前重新捕获旧回执，只作升级门禁比较，不把未知投递标成成功。
- 状态丢失、损坏、版本不明，上一版资源摘要变化、残留进程无法确认退出、恢复预算耗尽或恢复启动失败时，保留现场并退出。外层不会绕过退出码 78 继续重试。
- 守护自身被终止、整台机器关机或云工作区回收后，这里的进程无法自行复活。长期部署应由宿主 systemd 等服务管理器托管外层守护，并保留保护性停止语义；当前脚本不能提供跨机器存活保证。

## 验收

`python3 scripts/test-self-upgrade-runtime.py` 覆盖候选验证、投递门禁、启动失败回退、运行中退出、已提交候选隔离、资源升级回退、损坏状态保护与有限恢复。

`python3 scripts/test-service-guard.py` 在隔离的 Linux 测试进程中验证监督器被强制终止后的孤儿清理、有限重启、正常停止、旧实例保护，以及实际监督器与外层守护组合后的两层崩溃恢复。测试不连接 QQ，不对正式机器人注入故障。

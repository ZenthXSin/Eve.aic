## 持续认知与内生驱动（当前实施计划）

状态：数据契约与持久化切片已随 PR #73 合入；驱动评估、唤醒和自主循环是当前下一切片。详细契约见[认知循环](./认知循环.md)。

### 已完成：结构化状态与持久化

- 定义层：独立认知 API，定义主体/来源/权限、交流事件、STATE、DRIVES、AGENDA、目标、反馈和错误；不依赖厂商协议或 Kernel 私有类型。
- 实现层：内置认知状态插件，通过公开 StateStore 保存版本化快照，提供只读快照与按修订更新的公开服务，更新失败保留已有状态。
- 组合层：终端、QQ 和内部唤醒连接同一主体，由来源映射策略绑定事件；执行仍交给 Control/Session，模型角色只提供能力。
- 首个 PR 验收：未完成目标跨独立进程恢复；同主体不同来源访问边界；并发旧修订拒绝；损坏/未知版本/保存失败不覆盖原状态；完成或执行不确定目标不恢复为可执行。补齐示例、格式、Clippy 和 Ubuntu/Windows/Rust 1.89 检查。

### 下一项：无需新消息的闭环

- 持久化 Ready 目标在重启后由内部唤醒选出；一次只执行一个目标，记录驱动力依据、预算、选中理由、停止条件和结果反馈。
- 用户输入可调整优先级，显式取消先等待现有工具与会话收尾；Pending/Unknown 或反馈保存失败进入阻塞，不自动重放。
- 只在目标验证条件满足且执行/反馈保存成功后标记完成。无候选目标、预算耗尽或等待外部信息时休眠，避免反复模型自聊。
- 完整验收：没有新输入时推进一次本地任务；中途取消与完成竞争、崩溃窗口恢复、旧工具零重放；内部记录不自动发送 QQ，外部输出按来源/权限路由。
- 记录单次唤醒到准入、取消收尾、恢复延迟、模型/工具次数和空闲资源。离线结果与真实模型结果分别记录。

### 下一切片的实现顺序与验收门槛

1. 增加可替换的驱动/议程策略与公开循环契约；从 Ready 且未失效的目标生成理由和排序，不消费 Blocked 或终态。唤醒通过有界队列合并事件与定时信号，无候选时不调用模型。
2. 用 CAS 保存 Executing 和唯一尝试 ID 后才准入 Control；并发唤醒只能提交一次。组合层连接受限的模型/工具执行预算，实际计数与总期限必须生效，不能仅保存预算字段。
3. 从实际 ControlReport、Session 提交和明确验证条件生成反馈，保存成功后发布终态。取消/超时先 cancel 并 wait；Pending/Unknown、反馈保存失败或恢复中断保持阻塞，不自动重试旧工具。
4. 验收进程 A 保存 Ready，进程 B 无新输入也完成 loopback 模型与本地 echo，并持久化验证反馈；进程 C 旧任务零重放。覆盖重复唤醒、并发 CAS、取消与完成竞争、预算耗尽、无效配置、反馈保存失败和损坏恢复。
5. 组合层在 Kernel 停止前关闭唤醒、取消并等待在途执行，检查旧句柄和目录锁释放。补齐认知唤醒/空闲/取消的性能指标；延迟预算超限 warning，正确性与超时失败阻断。

首个闭环只推进一个本地目标，不自动向 QQ 发送内部记录。随后独立推进生产 QQ 控制、受限辅助模型及最小长期记忆/语义检索；Jev 保持 TODO。

## Phase 0：文档与边界

目标：确定项目原则、内核边界和插件契约。

- 建立文档目录
- 确定 Rust Runtime
- 确定单进程优先
- 确定可信静态插件模式
- 确定 `plugin-api` 与 `kernel` 的边界

## Phase 1：Plugin API

目标：定义不依赖 Runtime 内部实现的插件接口。

- `Plugin`
- `PluginManifest`
- `PluginContext`
- `PluginInfo`
- `PluginDependency`
- `Permission`
- 句柄类型和错误类型

完成条件：插件只能通过 Context 访问 Runtime 能力。

## Phase 2：Kernel Runtime

目标：实现最小插件运行内核。

- Runtime 状态
- Plugin Registry
- Dependency Graph
- 生命周期状态机
- Plugin Scope
- 自动资源清理
- 启动失败处理
- 反向停止顺序

完成条件：一组互相依赖的插件可以稳定启动和停止。

## Phase 3：基础服务

目标：让插件能够真正协作。

- Event Bus
- Service Registry
- State Store
- Task Manager
- Logger
- Permission Checker

完成条件：插件可以通过事件、服务、状态和任务完成协作。

当前进度：上述六项均已提供抽象接口和默认实现，日志额外提供内存后端，任务支持自定义类型与调度。已有运行示例及自动化验收，进入 Phase 4。

## Phase 4：恢复与诊断

目标：验证长期运行基础。

- 状态持久化
- Runtime 重启恢复
- 插件状态查询
- 任务查询
- 错误诊断
- 清理错误汇总
- 基础回归测试

完成条件：Runtime 停止后重新启动，插件状态和运行结果可以恢复。

当前进度：文件状态后端、独立进程恢复、插件清单和任务查询、结构化停止错误汇总均已实现并有实际验收。恢复范围是字节状态，插件负责重建订阅、服务和任务。Windows、Ubuntu 的完整 CI 及 Rust 1.89 编译检查已接入；启动与清理 panic 复用错误收尾路径，已准入的生命周期操作由宿主独立持有，取消等待后继续执行并保留可查询结果。

## Phase 5：插件扩展边界

已开始实现插件扩展的基础契约：清单版本采用 SemVer，依赖范围在注册和启动前校验；宿主可安全卸载已完成收尾的插件且保留状态，为后续插件发现、更新和版本化协议提供共同入口。

已实现依赖启动全图预检并完成本地验收：单目标检查可达依赖，全部启动先检查全部根节点，再执行任何启动回调；预检失败不改变插件状态，也不触发启动或清理。具体边界见 ADR-0025，验收命令和场景见[执行书](./执行书.md#依赖启动预检验收)。

静态插件工厂与目录是本阶段的基础交付，继续分离定义、实现和组合层；最小 LLM 工具闭环按下述 Phase 6 独立推进。

静态插件工厂与目录已完成：`plugin-api` 提供 `PluginFactory`、`PluginCatalog` 契约，Kernel 提供进程内目录实现。目录支持同一 ID 的多个版本，但只接受精确 `(PluginId, Version)` 查找；登记时校验并保存清单快照，创建后再次校验完整清单。目录不启动插件、不自动求解依赖、不下载或更新，也不持久化工厂；宿主仍显式将实例交给 Kernel 管理生命周期。

插件扩展的后续评估项：WASM、独立进程、版本化协议、安装更新、沙箱与资源配额。

## Phase 6：最小 LLM 工具闭环

目标：在不改变 Kernel 生命周期边界的前提下，建立可替换 Provider 与插件化上下文、工具能力之间的确定性调用闭环。

已实现：`eve-llm-api` 是独立定义层，Runtime 持有模型请求和工具调用批次循环；Provider、Context、Memory、Tool、Channel 均可替换。每个工具声明并发策略，未声明时按默认串行作用域执行；Runtime 对并行安全调用设置最大并发数、逐项超时和协作式取消。并发上限默认值为 `10`，由后续配置服务提供已校验的每轮快照，配置契约和自举留在 #32。协议、错误、上下文槽位和工具绑定规则见[LLM 工具调用](./LLM工具调用.md)及 ADR-0028/0029。

交付顺序：

1. [已完成] 新增 `eve-llm-api`，定义 Provider、Context、Tool、消息和错误；为 Runtime 增加只读插件清单快照查询所需的最小诊断契约。
2. [已完成] 以确定性 Mock Provider、一个 Context 插件和多个 Tool 插件实现调用批次闭环，提供示例与无网络集成测试；覆盖并发上限、串行作用域、逐项超时和部分失败。
3. [实现、本地 HTTP 与真实模型验收完成] `eve-llm-openai` 已支持 Responses 文本/函数调用批次与 Unsupported 路径；密钥由宿主提供。本地服务器已验证文本请求、插件工具执行与结果回传、错误、超时和取消；`openai_responses` 通过配置服务构造 Provider/Host，已在 gpt-5.6-sol、reasoning none 下通过真实文本和一次插件工具往返验收；详见 OpenAI 接入记录。
4. [已实现、验收完成] `eve-session-api` / `eve-session-plugin` 借助 StateStore 实现最小会话恢复；`SessionLlmHost` 已有多轮、Responses HTTP、并发、失败/取消与保存失败验收，独立进程示例验证完整工具历史、Pending → Interrupted 和旧工具零重放。具体语义见[会话恢复](./会话恢复.md)，追踪 #43 / PR #44。真实 API 多轮与 reasoning 续传后置；Jev 与可打断会话继续由 #24、#29 跟踪。

5. [已实现，验收见 PR #46] Responses SSE、自有异步流事件、工具进度及会话保存通知；覆盖慢消费者/断开、取消、保存失败和四次独立进程恢复。默认非流式，真实流式 API 未复验；消息控制与 Jev 继续由 #29 交付。详见[流式输出](./streaming.md)。

完成条件：Mock 闭环实际运行，覆盖直接回复、多个工具调用、并发上限、串行作用域、未知工具、权限和参数拒绝、工具失败/超时/取消、Provider 错误与超时、Service 缺失、非法协议和轮数上限；真实 Provider、会话恢复和流式交互不是第一个切片的前置条件。


## 模型角色与配置（后续规划）

目标：通过配置服务为不同认知职责提供可替换的模型，避免把具体供应商、模型名称或单一模型能力写死在 Runtime 和插件中。配置定义与显式 primary 接线已交付，其余角色消费和统一路由仍按下述计划推进。

| 角色 | 主要职责 | 默认边界 |
| --- | --- | --- |
| 主模型 `primary` | 多轮对话、复杂推理、任务规划、工具编排和最终回复 | 可按能力声明使用对话、结构化输出、工具调用、流式或 reasoning |
| 辅助小模型 `auxiliary_small` | 意图预分类、路由、抽取、短摘要、记忆压缩和低风险预处理 | 默认只返回受限结构化结果，不直接执行工具或产生外部副作用 |
| Jev 模型 `jev` | 沿用现有 Jev 方向，承担消息关系、意图/修订判断和评估类请求 | 只输出带置信度的判断结果，不注册工具；规则路径和显式回退保持可用 |
| 语义模型 `semantic` | 向量化、语义检索、相似度、重排、聚类和记忆关联 | 可以是 embedding 或 rerank 模型，不要求生成对话文本，不执行工具 |

配置原则：

- 每个角色独立配置 Provider、模型标识、能力声明、上下文/输出限制、超时、并发和成本预算；同一个 Provider 或模型可以被多个角色复用。
- 凭据只保存为宿主管理的引用，不进入普通模型配置；角色配置不能绕过现有权限和生命周期检查。
- 角色所需能力必须在装配时校验，例如主模型的工具调用、Jev 的结构化判断和语义模型的向量维度；能力不匹配直接报告配置错误。
- 模型选择按请求边界取得快照，在途请求继续使用原快照。配置更新不应改变正在执行的轮次。
- 回退链必须显式配置并记录原因。可选角色不可用时可以走规则、禁用该能力或使用指定回退，不静默把所有请求转给主模型。
- 诊断记录角色、Provider、模型、延迟、用量、置信度和回退原因；默认不记录提示词正文、密钥或敏感内容。
- Web 管理面板后续显示各角色的配置状态、健康状态和回退情况，但不直接调用模型。

交付顺序：

1. 在配置 API 中定义角色标识、通用字段、角色能力和版本化 Schema。
2. 分离对话模型、Jev 判断和语义模型的公开适配契约，明确 Provider 与模型能力映射。
3. 在 Runtime/Context/Session/消息关系/Memory 装配层实现按角色路由和每请求快照。
4. 增加规则回退、超时/取消、预算、并发、审计和失败降级语义。
5. 用 Mock、本地 HTTP 和真实模型分别验收正确路由、结构化输出、质量、延迟、成本和恢复行为。
6. 将配置、健康检查、回退原因和权限审计接入 Web 管理面板。

依赖：现有配置插件与普通配置快照、`eve-llm-api`/Provider 契约、现有 LlmRelationJudge 与 Jev 适配方向、Context/Memory 能力，以及 Web 管理面板的 Control API。当前状态：四类模型角色配置与固定快照已随 PR #55 合入；PR #70 的显式 primary 装配已合入。PR #71 的每轮主模型解析已实现并验收；辅助/语义角色消费和统一路由仍待实现。Jev 继续 TODO。

## Web 管理面板（后续规划）

目标：提供 Eve 的浏览器控制面，统一查看 Runtime、Session、Task、事件和人工控制；不承担 Kernel 生命周期决策，也不直接执行小模型或工具。

当前状态：已纳入后续计划，暂不展开具体实现。现有 `eve-control-api`、`eve.control` 插件、Session/Runtime 控制能力作为后端前置；浏览器前端、HTTP/WebSocket 网关、认证授权和部署方式待后续细化。

初步范围：

- 实例健康、插件、会话、任务、日志与事件流查看
- 暂停、取消、恢复、重试和待确认操作
- 查看主模型、Jev/小模型判断、置信度与回退原因
- 通过 Control API 访问，不让浏览器直接调用模型或工具
- 后续再确定前端技术、权限模型、远程访问、审计和部署方式

依赖顺序：先稳定 Control API、Session/Runtime 事件语义和配置能力，再实现最小面板；记忆管理、插件安装更新和完整运维能力后置。

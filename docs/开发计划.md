# EVE.AIC 开发计划

## Phase 0：文档与边界

目标：确定项目原则、内核边界和插件契约。

- 建立文档目录
- 确定 Rust Runtime
- 确定单进程优先
- 确定可信静态插件模式
- 确定 `plugin-api` 与 `kernel` 的边界

## Phase 1：Plugin API

目标：定义不依赖 Runtime 内部实现的插件接口。

- `Plugin`
- `PluginManifest`
- `PluginContext`
- `PluginInfo`
- `PluginDependency`
- `Permission`
- 句柄类型和错误类型

完成条件：插件只能通过 Context 访问 Runtime 能力。

## Phase 2：Kernel Runtime

目标：实现最小插件运行内核。

- Runtime 状态
- Plugin Registry
- Dependency Graph
- 生命周期状态机
- Plugin Scope
- 自动资源清理
- 启动失败处理
- 反向停止顺序

完成条件：一组互相依赖的插件可以稳定启动和停止。

## Phase 3：基础服务

目标：让插件能够真正协作。

- Event Bus
- Service Registry
- State Store
- Task Manager
- Logger
- Permission Checker

完成条件：插件可以通过事件、服务、状态和任务完成协作。

当前进度：上述六项均已提供抽象接口和默认实现，日志额外提供内存后端，任务支持自定义类型与调度。已有运行示例及自动化验收，进入 Phase 4。

## Phase 4：恢复与诊断

目标：验证长期运行基础。

- 状态持久化
- Runtime 重启恢复
- 插件状态查询
- 任务查询
- 错误诊断
- 清理错误汇总
- 基础回归测试

完成条件：Runtime 停止后重新启动，插件状态和运行结果可以恢复。

当前进度：文件状态后端、独立进程恢复、插件清单和任务查询、结构化停止错误汇总均已实现并有实际验收。恢复范围是字节状态，插件负责重建订阅、服务和任务。Windows、Ubuntu 的完整 CI 及 Rust 1.89 编译检查已接入；启动与清理 panic 复用错误收尾路径，已准入的生命周期操作由宿主独立持有，取消等待后继续执行并保留可查询结果。

## Phase 5：插件扩展边界

已开始实现插件扩展的基础契约：清单版本采用 SemVer，依赖范围在注册和启动前校验；宿主可安全卸载已完成收尾的插件且保留状态，为后续插件发现、更新和版本化协议提供共同入口。

已实现依赖启动全图预检并完成本地验收：单目标检查可达依赖，全部启动先检查全部根节点，再执行任何启动回调；预检失败不改变插件状态，也不触发启动或清理。具体边界见 ADR-0025，验收命令和场景见[执行书](./执行书.md#依赖启动预检验收)。

静态插件工厂与目录是本阶段的基础交付，继续分离定义、实现和组合层；最小 LLM 工具闭环按下述 Phase 6 独立推进。

静态插件工厂与目录已完成：`plugin-api` 提供 `PluginFactory`、`PluginCatalog` 契约，Kernel 提供进程内目录实现。目录支持同一 ID 的多个版本，但只接受精确 `(PluginId, Version)` 查找；登记时校验并保存清单快照，创建后再次校验完整清单。目录不启动插件、不自动求解依赖、不下载或更新，也不持久化工厂；宿主仍显式将实例交给 Kernel 管理生命周期。

插件扩展的后续评估项：WASM、独立进程、版本化协议、安装更新、沙箱与资源配额。

## Phase 6：最小 LLM 工具闭环

目标：在不改变 Kernel 生命周期边界的前提下，建立可替换 Provider 与插件化上下文、工具能力之间的确定性调用闭环。

已确定：`eve-llm-api` 是独立定义层，Runtime 持有模型请求和工具调用批次循环；Provider、Context、Memory、Tool、Channel 均可替换。每个工具声明并发策略，未声明时按默认串行作用域执行；Runtime 对并行安全调用设置最大并发数、逐项超时和协作式取消。并发上限默认值为 `10`，由后续配置服务提供已校验的每轮快照，配置契约和自举留在 #32。协议、错误、上下文槽位和工具绑定规则见[LLM 工具调用](./LLM工具调用.md)及 ADR-0028/0029，尚未写入代码。

交付顺序：

1. 新增 `eve-llm-api`，定义 Provider、Context、Tool、消息和错误；为 Runtime 增加只读插件清单快照查询所需的最小诊断契约。
2. 以确定性 Mock Provider、一个 Context 插件和多个 Tool 插件实现调用批次闭环，提供示例与无网络集成测试；覆盖并发上限、串行作用域、逐项超时和部分失败。
3. 在独立 `eve-llm-openai` 中以 Responses API + reqwest 接入 OpenAI Provider，先验证可无损的文本/函数调用批次子集与 Unsupported 路径；密钥仅由宿主提供，完成文本请求和一次真实工具调用 smoke test。
4. 由会话或记忆插件借助现有 StateStore 实现最小会话状态恢复；随后回顾 VCPToolBox 能力缺口。Jev 实验与可打断会话分别后置到 Issue #24、#29。

完成条件：Mock 闭环实际运行，覆盖直接回复、多个工具调用、并发上限、串行作用域、未知工具、权限和参数拒绝、工具失败/超时/取消、Provider 错误与超时、Service 缺失、非法协议和轮数上限；真实 Provider、会话恢复和流式交互不是第一个切片的前置条件。

## 配置能力节点（Issue #32）

第一切片已实现 `eve-config-api` 定义层、`eve-config-plugin` 内置实现，以及仅依赖公开契约的配置消费者。普通配置支持版本化 Schema、默认值 < 环境变量 < 配置文件、正数并发上限（默认 10）、立即替换/仅新请求、重启字段、CAS 更新、20 个自动备份与手动固定、回滚和严格文件恢复；停止/失败回滚后释放目录锁并使旧服务失效。详见[配置管理](./配置管理.md)。

后续切片继续实现内置加密密钥库、主密钥初始化与恢复、密钥引用、凭据代理、外部查看 2FA、插件版本/内容哈希授信及检查工作流。当前实现拒绝敏感和加密字段，#32 尚未完成。普通配置服务可独立于 LLM Mock PR 合并；之后再将每轮配置快照和凭据引用接到真实 OpenAI Provider，不把普通 JSON 字符串当作密钥传输通道。

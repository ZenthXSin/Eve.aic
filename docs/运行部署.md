# 独立运行装配

`deployment/main.ts` 只生成私有配置和待安装的 systemd unit；它不启动服务、不发送 QQ、不调用模型，
不会把完整配置打印到终端。`--dry-run` 不落盘，`--stage` 使用排他写入，已有密钥或配置会使装配失败，
不能借重跑静默轮换运行凭据。正式切换由操作者检查产物后执行。

运行分为五个服务：独立所有权守护、共享执行后端、独立 QQ 适配器、监督进程、管理面板。
在线与观察实例由监督进程启动；两个实例共享后端事实和动作回执，每个实例有独立凭据、证明、
脚本目录、内核目录及观察覆盖层。实例配置不包含模型 API key、QQ 凭据、守护管理员/出口密钥。私有根和
instances 父目录仅开放遍历 权限（0711），root 管理密钥为0600，每实例私有配置目录 root:实例GID
0750，其中配置、密钥、提示与proof均为 root:实例GID
0440，只允许实例读取而不能修改或换名；实例运行目录属于其UID、0700。实例只拿自身
的证明、控制密钥、凭据，以及 runtime/phone 桥接密钥副本和身份提示。连接地址放在
`runtimeDirectory/public/{guardian,runtime,phone,upgrade}.json`，目录0755、连接文件0644，内容没有密钥。
`KillMode=control-group` 负责服务结束时清理本服务派生命令。

## 准备

1. 完成源码检查并提交。用 `supervisor/source.ts` 的 `pinSource()` 固定完整 40 位 commit，
   获得通过机械校验、包含逐文件摘要的 SourceArtifact。产物放在 `/opt/eve/releases` 等可遍历路径，
   Deno 安装在 `/usr/local/lib/eve/deno` 等可执行路径；二者不能放在
   `/root`。部署和每次实例启动均重新验证摘要。
2. 创建 `eve-exec`、`eve-instance-a`、`eve-instance-b` 三个系统用户，记录非零且彼此不同的 UID/GID。
   命令/文件后端使用 eve-exec，两个实例轮流使用独立实例 UID；候选无法读取旧实例私有上下文和
   守护管理员凭据。脚本 worker 本身没有任意命令执行权限。命令通过独立 systemd transient unit
   持有进程组，撤销时按整个 cgroup 终止，防止派生后台进程逃逸。
3. 选择 `/etc/eve-private` 等新私有配置目录、`/var/lib/eve` 新运行目录、现有 QQ
   数据目录、独立可遍历的工作空间（例如 `/var/lib/eve-workspace`）。工作空间不能位于 `/root`
   或私有运行目录下；勿把 root 密钥复制进去。 仅工作空间归 `eve-exec` 所有。可在这里放供 Eve
   编辑和提交的源码仓库，运行的固定源码产物 保持 root
   所有。所有祖先目录必须允许命令用户遍历。`prepareWorkspaceRepository()` 可按固定分支 clone
   独立完整历史，移除原仓库 origin，不使用 shared 对象链接，并仅将新工作仓库交给专用 UID。
4. 保留当前私有 `config.json` 和 QQ 数据、已验证主人绑定、原始收件与出站回执，不导入旧聊天记忆。
   沿用配置必须为 private QQ、sandbox false、有明确已绑定 owner 和 Chat 模型配置。
5. 写仅 root 可读的选项 JSON，字段对应 `DeploymentOptions`，另加 `existingConfigFile`、
   `unitDirectory`。其中 `source` 是上述 SourceArtifact，`commandIdentity` 为命令用户的 UID/GID，
   `instanceIdentities` 是两个实例用户 UID/GID 对象的数组。 `repositoryDirectory` 默认工作空间内的
   source；`artifactDirectory` 建议 `/opt/eve/releases`。 路径必须绝对且无空格、百分号或 shell
   转义。`dailyTokenBudget` 默认 200000000，时区默认 Asia/Tokyo。

```sh
/usr/local/lib/eve/deno run --allow-read deployment/main.ts --dry-run /private/options.json
bash deployment/install.sh --stage /private/options.json /usr/local/lib/eve/deno
```

装配后的共享设置默认 `paused:true`，便于先核实出口、绑定、预算和面板，不会在首次拉起时自动花费模型。
语义检索模型接入保留为 TODO，配置不生成 semantic 项。全文检索/记忆事实仍可用。

## 切换与核实

部署前归档当前 adapter unit、当前源码 commit、私有配置和服务状态；归档只放 root 私有目录。
核查五份待安装 unit 的 source 目录、工作空间、可写目录和配置路径，再安装到 systemd 并
daemon-reload。 先启动 guardian，确认本地连接文件和暂停状态；现有 QQ 仍可保持运行。 第一次将 QQ
adapter 改为新固定源码和守护出口需要一次短重启，必须继续使用原 QQ 数据目录，
随后先核实连接和已绑定主人。部署配置显式开启 `qq.captureActivationBoundary`，适配器在首次开放查询前
为原入站、出站记录建立同一真实时间线，并排他保存 `activation-boundary.json`。首次种入意识时只使用其
通知序号边界，不把旧消息正文自动注入意识，也不修改手机阅读标记；边界后的新消息仍正常通知。不要用
入站条数猜测该序号，也不要在普通重启时覆盖首次边界。日后的候选切换由 supervisor 完成，QQ adapter
不随实例重启。

若需离线种入首次启动事件，须先完成上述边界捕获，并保持 runtime、supervisor、admin
停止，避免与意识账本写锁冲突。 完成种子后启动 runtime，再启动
supervisor/admin，通过本机管理面板查看状态、独立预算和暂停原因，确认只有一个有效在线实例。
面板仅绑定 127.0.0.1；通过已有认证通道访问，口令保存在私有 token 文件，不放 URL、日志或源码。
正式恢复意识流后，再做真实私信往返和一次用户已授权的上线通知，保存事实回执；机械测试不能冒充实际送达。

回退应先暂停/排空出口，通过监督流程授予更高 epoch，再恢复已固定的旧实例。不要删除共享账本、
未知动作回执或未确认候选的记录；不要手工把旧 proof 改成当前 epoch。

每轮测试/装配结束确认本轮构建进程已退出，清理临时预演、验证 DENO_DIR 和重复下载；保留实际运行的
源码产物、唯一数据和必要的回退版本。检查剩余磁盘空间并记录。

# EVE.AIC 第一阶段执行书

## 执行原则

1. 先确定边界，再写实现。
2. 先让最小闭环运行，再增加抽象。
3. 插件只能通过 Context 访问 Runtime。
4. 内核不硬编码 Memory、LLM、Personality 等认知模块。
5. 所有生命周期资源必须能够自动清理。
6. 每个阶段都必须有可执行的验收场景。
7. 不为了未来可能的需求提前引入复杂插件协议。
8. 自动推进既定计划，遇到需用户判断的关键问题再询问；每次 PR 前检查已有评论、Issue 和其他 PR。

## 当前执行顺序

```text
文档边界
    ↓
Plugin API
    ↓
Kernel Skeleton
    ↓
Registry / Dependency
    ↓
Lifecycle / Scope
    ↓
Event / Service
    ↓
State / Task
    ↓
Failure / Cleanup
    ↓
Shutdown / Recovery
```

## 第一条验收链（已实现）

```text
Runtime 启动
    ↓
注册 ServiceProviderPlugin
    ↓
注册 EventConsumerPlugin
    ↓
消费者声明并解析提供者依赖
    ↓
启动消费者，自动启动提供者
    ↓
消费者获取 Service
    ↓
提供者发布 Event
    ↓
消费者收到事件并写入 State
    ↓
停止消费者，再停止提供者
    ↓
清理监听器和 Service
    ↓
启动失败插件并验证资源回滚
```

运行 `cargo run -p eve-runtime` 实际执行以上验收链；`cargo test --workspace` 同时验证后端替换、权限拒绝、类型冲突、事件重入、状态隔离、停止顺序和回滚错误。

任务管理已有独立测试；持久化 State 和重启恢复使用下述独立验收，不作为基础协作验收链的前置条件。

## 暂停条件

遇到以下情况时，应先回到设计讨论，不继续堆代码：

- 插件需要访问 Runtime 私有结构
- 两个插件直接互相调用内部方法
- 生命周期状态无法解释
- 失败后无法清理已经创建的资源
- 状态恢复需要依赖具体插件实现细节
- 为了实现一个功能而引入动态 ABI 或微服务

## 任务验收（已实现）

运行示例同时执行前台立即、延迟、指定时间和三次重复任务，共六次，随后停止后台周期任务。独立任务测试采用 Tokio 虚拟时钟验证调度与共同截止时间，并覆盖停止准入、任务错误与 panic、实际次数、失败回滚、丢弃等待、可替换后端和未退出任务诊断。

扩展验收：仅依赖定义层的插件自行定义 `WriteStateTask` 和递增间隔调度，实际完成三次状态写入，并将同一类型用于后台周期执行。独立扩展测试验证事件触发、调度实例隔离、次数上限、提前结束、取消等待、工厂及调度失败，以及完成后释放工厂捕获资源。

## 日志验收（已实现）

示例插件通过 Context 记录消息处理、任务完成和预期启动失败，默认写入标准错误；宿主停止后显式刷新。Runtime 测试注入内存后端，检查三条日志的插件来源、级别和字段。独立日志测试覆盖级别过滤、按容量淘汰、并发短写不交错、控制字符转义、后端错误与启动回滚、替代实现重入 Context，以及任务收尾和旧 Context 的日志边界。

## 状态恢复验收（已实现）

连续两次运行 `cargo run -p eve-runtime --example state_recovery -- ./target/state-recovery-demo`，独立进程依次读取“无”和“1”，写入“1”和“2”。自动化测试覆盖跨进程锁、重新创建 Kernel 后恢复、任意字节、严格格式校验、并发提交与 Windows 实际替换失败，均使用隔离临时目录。

## 诊断验收（已实现）

协作示例通过 `RuntimeInspector` 查询四个插件的终态和残余任务，验证正常停止与预期失败的区别。独立测试检查清单排序、快照独立性、启动/停止中间状态、共享依赖只停止一次、多插件失败保留、同插件不同阶段失败保留，以及退出检查失败或残余任务必然报告失败。

## 生命周期 panic 验收

隔离范围为插件启动和 Cleanup 两个入口，分别覆盖同步工厂调用与所返回 Future 轮询中的 Rust unwind panic。验收要求：

1. 启动入口发生 panic 后返回错误，插件进入 `Failed`；已创建的任务、服务和订阅按普通失败路径收尾，旧 Context 失效，本次新启动的依赖被回滚。
2. Cleanup 工厂或其 Future 轮询发生 panic 后，仍逆序执行剩余回调，继续停止其他插件，并在报告中保留出错插件和清理阶段。
3. 任务均确认退出时，Cleanup panic 可与 `Stopped` 同时出现；任务未退出或无法确认退出时仍为 `Failed`，禁止自动重启。重复停止不重试已经失败的一次性 Cleanup。
4. 失败插件收尾与依赖回滚同时出错时，保留启动原因和回滚错误，不因新的 panic 丢失原始故障线索。
5. 运行工作区测试、格式与 Clippy 检查，并实际执行受影响示例；以运行结果确认验收，不将文档列出的要求视作已经通过。

默认 panic hook 仍输出诊断。该隔离边界不承诺恢复 `panic=abort`、双重 panic 或析构 panic。宿主取消等待不取消已经准入的生命周期操作，应保持执行器运行并取得实际终态；自定义后端应按契约返回 `Err`。具体接口边界和错误解读见[插件开发](./插件开发.md#启动与清理的-panic-边界)与[运行时诊断](./运行时诊断.md#生命周期-panic-的诊断)。

## 生命周期操作验收

运行 `cargo run -p eve-runtime --example lifecycle_operations --locked`，通过 `RuntimeLifecycle` 显式提交，暂停 Cleanup 使一次等待超时，确认操作仍在运行；放行后再次等待实际终态，检查清理执行、重复读取和确认移除报告。该场景的完整语义见[生命周期操作](./生命周期操作.md)。

边界验收要求：

1. 提交 Future 尚未轮询，或等待准入锁时被取消，均不修改插件；默认 Kernel 缺少 Tokio 执行器时拒绝提交。
2. 已准入操作不因调用方取消等待而中止；兼容包装器正常返回自动确认，丢弃等待则保留结果。
3. 容量满时拒绝新请求而不覆盖旧记录；零容量拒绝全部提交。运行记录不能确认，未知 ID 确认返回 `false`。
4. 已经取得记录的等待者，在其他宿主确认后仍返回原终态；确认后新开始的等待报告未知 ID。兼容包装器同样保留自己的结果。
5. 操作执行任务尚未首次轮询便被执行器丢弃时，记录 `Interrupted` 而不修改插件或隔离 Kernel，允许在运行中的执行器重新提交。
6. 操作已经开始后中断时，全局隔离 Kernel、关闭 Context，将原来等待依赖、启动中、活跃和停止中的插件标为 `Failed`。这种失败表示 Runtime 不可继续；异步清理和捕获资源立即释放均不作保证。

操作报告仅存于内存，不提供进程恢复，也不自动撤销成功的状态写入。提交前完成相关测试、格式、Clippy 和实际示例验收，以运行结果记录完成情况。

# 宿主内存测量

这里记录进程内存，不是模型 token。当前数据来自 Linux debug 构建，固定共享 target、两个构建任务、debug=0、incremental=0；基线提交为 `64f42b9`，优化补丁在同一工作区和配置测量。样本只连接本地模型和平台替身，不连接正式 QQ。

| 固定样本 | 优化前 | 优化后 | 含义 |
| --- | ---: | ---: | --- |
| 64 脚本版本、每版 128 KiB、八 scope，进程峰值 | 51,064 KiB | 35,316 KiB | 下降约 30.8%；账本均为 8,423,468 字节 |
| 同样本 64 版本阶段 VmRSS | 43,132 KiB | 27,348 KiB | 阶段采样，不是峰值 |
| 同样本重启后 VmRSS | 35,664 KiB | 27,504 KiB | 重启仍核验全部版本 |
| 6 MiB 模型响应提取 usage 的进程 VmHWM | 16,696 KiB | 10,632 KiB | 仅用量提取，不代表整个 HTTP 请求峰值 |

脚本事务只消除一次全账本复制与整份哈希序列化缓冲。独立事务候选仍保留，JSON 校验字节不变；旧版本、回执、CAS、Unknown 与工具步数上限均不变。账本仍全量常驻，这不是冷存按需加载。

模型用量提取通过结构化反序列化只保留 `usage` 字段，跳过 `choices/output` 的重复内存分配；之前的严格响应协议校验保持。未知字段依然必须是有效 JSON，原响应正文未截断；重复 usage 键保留旧 Value 解析器的最后一项覆盖语义，false/null 与坏 JSON 的结果也保持一致。固定响应为 6,291,551 字节，输入与输出 token 字段校验结果相同。

## 独立测量

- `memory_profile` 示例：64 个版本逐次发布、激活，关闭并重启；源码与数据只在本样本临时目录。峰值由独立子进程的 `getrusage(RUSAGE_CHILDREN)` 记录，耗时 28.76/28.79 秒。
- `rust_memory_profile` 示例：八 scope、32 次真实隔离 Rust 编译、激活及执行。流式哈希补丁后宿主峰值 11.24 MiB，32 项缓存 VmRSS 8072 KiB；编译和链接子进程合计峰值 142.63 MiB。耗时 42.45 秒，测量器在剩余磁盘低于 64 MiB 时停止新增编译；本次未触发，临时缓存已清理。没有修前对应样本，不声称 Rust 缓存降幅。缓存保留的是路径与磁盘产物，不能当作 32 份常驻二进制。
- `cargo test -p eve-llm-openai --lib large_response_usage_memory_profile -- --ignored --nocapture`：独立进程中的大响应 usage 读取，打印处理前后的 VmRSS/VmHWM；非 Linux 不提供这两个指标。
- 真实 QQ 宿主 76 轮、多 scope、原始档案引用与重启基线：第一进程峰值 104.0 MiB，退出前 20 个采样平均 102.9 MiB；重启进程峰值 90.1 MiB，末段平均 85.9 MiB。递归子进程峰值另为 123.2/117.7 MiB。此长程样本尚无同场景优化后对照，不能用上述局部改进比例外推。

主进程与子进程峰值分别记录，不能相加声称是同时总峰值。退出前采样平均不等同于静置空闲内存。分配器、操作系统与样本大小会影响数值；Windows 内存表现尚未实测。后续冷账本、Session 快照副本和召回加载应继续使用独立基线及相同样本验证，不能以删原文、减少工具步数或弱化 scope 校验换取占用下降。

## 归档召回分页对照

2026-10-30，`eve-memory-plugin/examples/memory_profile.rs` 使用同一份真实文件库中的 320 轮合成交流，每轮用户与助手正文各约 30,000 字节，原文合计约 19.2 MB。seed、full、scan 分别在独立进程运行；两种读取均执行三次相同召回，JSON 输出逐字一致。样本不调用模型或 QQ；结束后删除本次临时样本，正式数据不变。

| 读取方式 | 独立进程峰值 RSS | 三次读取及固定 2 秒采样等待 |
| --- | ---: | ---: |
| full：先取完整归档快照，再通过兼容游标召回 | 38,576 KiB | 11.819 秒 |
| scan：原生游标逐块读取 | 25,160 KiB | 11.773 秒 |

分页路径在该样本下降约 34.8%。两者都是本次代码和相同缓存预算，比较的是完整快照与原生分页入口，不是两个历史提交的整机对照。峰值由 Linux `wait4` 的 `ru_maxrss` 采集；时间包含共同的固定等待，不能当作纯召回延迟。解码缓存预算为估算堆字节 8 MiB，热层和紧凑唯一性索引仍占内存，不代表整个系统恒定内存或所有学习器都已经分页。

复现：构建 `cargo build -p eve-memory-plugin --example memory_profile`，对独立空目录依次执行 `memory_profile seed <目录> 320`、`memory_profile full <目录> 320`、`memory_profile scan <目录> 320`。读取结果可分别保存后逐字比较。相关 API/plugin 全目标测试 123 项通过，跨页归档期间固定修订的加强用例另外通过；严格 Clippy、工作区格式检查和应用库编译检查通过。`recovery` 示例在同一临时目录运行两次，修订保持 4，偏好保持撤销，模型请求与工具执行均为 0。

## 语义分段缓存载荷对照

2026-10-31，使用同一目录的 128 个真实压缩分段，每段 128 条合成索引、4096 维量化向量。两个独立 Linux 测试进程各逐段读取两遍，共核对 32,768 条向量；每次只持有当前段，在两个模式下都执行相同的文件类型、字节限制、SHA-256 和条目检查。没有模型、QQ 或正式数据调用，样本结束后删除临时目录。

| 缓存策略 | 常驻段数 | 估算缓存载荷 | 独立进程峰值 RSS |
| --- | ---: | ---: | ---: |
| 原按数量策略：最多 256 段，无载荷总字节限制 | 128 | 139,095,808 字节 | 144,556 KiB |
| 增加 32 MiB 缓存载荷预算 | 30 | 32,600,580 字节 | 39,396 KiB |

该样本峰值下降约 72.7%，两个进程核对的向量数和内容一致。比较的是本次代码中两种缓存策略，旧策略只在忽略的测试探针里启用，不是两份历史发布版或整机 Eve 的对照。载荷计入向量字符串、Vec、键与模型字符串的 capacity；不把 BTreeMap 节点、分配器或外部在途 Arc 算作缓存载荷，更不代表整个程序 RSS 上限。并发调用持有的值和单次混合召回布局仍须分别优化。

复现：`cargo test -p eve-semantic-plugin --lib semantic_cache_memory_profile -- --ignored --nocapture`。父测试生成样本，分别启动独立测量子进程，读取各自 `/proc/self/status` 的 VmRSS/VmHWM；完整父测试本次约 54.5 秒，不能当作纯召回耗时。正式运行始终同时使用 256 段与 32 MiB 载荷限制，没有增加配置入口。

## 上下文临时副本

2026-10-31，分层上下文的原文引用/建议缓存改为流式 SHA-256，仍覆盖完整 JSON 的每个字节，摘要与原 `to_vec` 编码逐字节对照一致；历史窗口和分层选择直接用 JSON 计数 writer 计算精确 UTF-8 大小。只为了哈希或长度而生成的完整 JSON 临时副本已移除。

协议核验增加借用入口 `ModelRequest::validate_parts`，原 `validate()` 调用同一实现；Session 完整轮次、运行时历史和选中历史直接借用切片核验，保留全部角色、工具调用/回执配对及定义唯一性检查。审核原话从后往前选满六条才复制，恢复原顺序，不截断正文，委派轮次和宿主事件规则保持。原始 Session 历史仍会在执行开始时恢复为完整目标会话，不能把这些副本优化当作已完成流式会话装载，也未测量本切片的整机 RSS 降幅。

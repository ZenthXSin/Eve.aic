# 子代理串行与并行

QQ 用 `--subagents` 启用 `run_subagent`，用 `--background-tasks` 启用持久后台任务。二者默认关闭，全功能配置开启。

- 串行：模型先调用一个子代理，拿到结果后在下一批调用另一个，可传递前一步结果。父轮次的工具批次上限必须允许多批，例如 `--max-tool-rounds 50`。
- 并行：模型在同一工具批次调用多个 `run_subagent`。工具声明 `ParallelSafe`，结果按原调用顺序回传，不按完成时间重排。
- 简单编程任务由 Eve 直接完成；中等及以上的编程任务默认交给 `agent_id="coding"`。其中可独立拆分的工作默认同批并行，逐项明确文件分工；不可拆分的任务只派一个，有依赖的步骤先取得前一步结果再继续，不为了并行重复工作或让多个执行者修改同一文件。
- `include_context=true` 可携带父会话的完整冻结历史，独立于当前任务说明并可压缩；关闭时须在 `task` 中写清背景。真实原话、可信身份和工具范围单独继承；叶子执行器不提供后台派发、子代理或条件触发器管理工具，不递归派生。

`runtime.tasks.subagent_concurrency` 默认 **10**，允许 1–10；环境变量 `EVE_SUBAGENT_CONCURRENCY`。面板保存后，新调用采用新上限，在途调用继续收尾。所有会话共用同一个计数，超过上限的调用按 FIFO 等待空位，父轮次取消时等待和执行一并取消；取消、错误和 Future 丢弃均释放名额。降低上限不强行终止已开始的调用。

后台任务的 `runtime.tasks.max_running` 独立配置，默认 2；本次不改变它。主任务与全部子代理共享剩余工具步数；工具并行槽位、父任务期限和每轮工具总数限制仍有效，所以设为 10 不保证每次都运行 10 个子代理。实际模型请求还受所选角色的 `max_concurrent_requests` 限制；主/辅角色各最多 5，所有主/辅用途合计最多 5。独立 coding 选用辅助角色时，面板 `runtime.models.auxiliary_small_max_concurrent_requests` 可设为 3，让可拆分的编程请求并行且为交流和蒸馏保留容量；显式已有配置不被提示或派发自行改写。

验证：`qq_tasks` 单元测试让前十项占位，第十一项等待并在释放后进入；`background_task_test.py` 用实际 QQ 宿主和本地模型替身同批派发十个子代理，门控核验五个实际模型请求重叠、另五个等待共用模型槽，再验收两项串行传递结果。`dual_model_effort_test.py` 另在同一父会话的一批调用中委派两个 coding，门控核验模型 HTTP 请求真实重叠、文件分工、完整回执、共享六步工具预算和独立稳定会话。以上不代表真实外部模型请求的吞吐保证。


子代理交回结果时，`completed` 仅表示冻结合同实际通过。未指定合同或证据不可核验返回 `status=returned_pending_verification`、`blocked=false`，父线程可据真实回执继续核验和整合；明确未完成事项返回 `status=blocked`、`blocked=true`。不能把两种结果都读作“编程无法进行”，也不能把待核验晋升成已完成。

# 连发合并

人在 QQ 上常把一句话分成几条连着发。QQ 宿主在准入前稍等一下，把同一人连发的几条纯文字合成一轮，让 Eve 看完再一次性回复，而不是每条各回一次。

## 规则

- 只合并同一会话（同一私聊，或同一群里的同一人）中尚未开始处理的纯文字普通消息。带图片或文件、引用了别的消息、命令，以及任务进行中按[消息关系](./消息关系.md)判断的消息不参与合并。
- 一条消息进入排队后，若同会话最后一条仍在 `debounce_ms` 窗口内就继续等；最多从第一条起等 6 秒、合并 5 条，合并后正文不超过 8192 字节。超出时剩下的消息照常排在后面。
- 同一会话严格按到达顺序准入：前面的消息还在等待时，后面的（包括带附件的）不能越过它。
- 合并后的会话输入是各条原话按顺序用换行连接；回复挂在最后一条消息上，前面的消息不再单独回复。
- 交互记忆按合并后的完整输入记录；表达训练仍在每条消息到达时按原话各自记录。

## 配置

“插件页面 → `runtime.chat_timing`”的 `debounce_ms`（环境变量 `EVE_DEBOUNCE_MS`），默认 1500，范围 0–10000 毫秒，0 关闭。每次准入时读取，修改即时生效。窗口会让每条消息的处理晚开始至多这么久。

## 持久化与恢复

- 回执始终保存每条消息的原话。整组被并入的消息和统一回复的目标一次原子提交；前面的状态为 `Merged`，并记录 `merged_into`（统一回复的那条消息 ID），目标为 `Processing`。提交后才通知通道结束前面的消息，不发送回复。写入失败保留原账本，容量不足不确认合并，避免中途退出留下悬空引用。
- 统一回复的那条按原有流程保存 Processing、ReplyPending、Sent 等状态；合并后的文本只用于本轮会话输入，不写进回执。
- 出现 `Merged` 后回执文档格式为 **4**。旧程序按未知版本拒绝启动，不会把被并入的消息误当作未处理。
- 加载时严格校验：`Merged` 必须有 `merged_into`，且指向同一应用、同一身份中顺序在后的非合并回执；不能带回复、分段或进展。不一致视为损坏，保留原字节、拒绝启动。
- 升级监督器支持格式 4，并按合并关系重建本轮输入来核对确切送达门；进度仍按既有发送状态判断，不能把合并记录当作已回复。回退必须使用兼容格式 4 的程序；便携包数据代际同步提升为 2。
- 等待中的消息尚未落盘；进程在等待期间退出时，这些消息与原来排队未处理的消息一样不会被补处理。重启不重放已合并或已回复的消息。

## 验收

`connectors/qqbot/test/debounce_test.py`：

- 两条连发合成一轮，模型只收到一次合并输入；前一条为 `Merged` 并指向后一条，后一条 `Sent`，回执格式为 4，重启后合并记录不变、不重放。
- 窗口为 0 时各自成轮；不同用户各自成轮。
- 带图片的消息打断连发，并且不会越过仍在等待的前一条。

`eve-qqbot-plugin` 单元测试覆盖 `Merged` 回执的校验与格式。
